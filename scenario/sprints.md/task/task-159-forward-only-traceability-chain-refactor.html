Context

Tron 2026-06-01 (verbatim, relayed via PO): the traceability chain is **forward-only**. The graph edges go: ``` Requirement → Task → (Subtask ∪ UseCase) → Class → Method ``` **Multiple requirements may address the same task** (a task can appear in `requirement.tasks[]` arrays of multiple requirements). **No back-refs:** a task does NOT carry a reverse pointer to its parent requirement(s); a UC does NOT carry a reverse pointer to its parent task or requirement; etc. Existing scenarios (post-T151/T152/T153/T155) carry reverse arrays that Tron now forbids: - `task.links.up → requirement` (anti-pattern) - `useCase.requirement` / `useCase.requirements[]` (T153/T152) - Any `*.parent` / `*.coverIn` style reverse field T159 strips these AND refactors T155's reverse-scan logic to NOT consume back-refs (T155's forward output `requirement.tasks[]` remains correct; its back-ref INPUT must be replaced by forward parsing from `requirements.md`).

Intention

### Why this task exists - Tron's directive corrects the data-model direction - Existing reverse arrays persist back-refs the model now forbids - T158 browser cannot render forward-only chain accurately while back-refs remain — T158 ACs depend on T159's cleanup ### Problems this task solves - Back-refs in scenario JSON contradict Tron's canonical chain - T155's reverse-scan logic reads anti-pattern input - T126 templates may surface reverse edges users see as "wrong-direction" ### How it solves them - Drop back-ref fields from LoaderDefaults (Task/UseCase/Class/Method) - One-shot migration strips existing back-refs from JSON - Refactor T155 closure: forward-only data sources (parse `requirements.md` forward bullets, not task `links.up`) - Standard documents the forward-only chain explicitly
