## Impl shape (3 links, each authoritative for a different fact)
1. **Task → CRs = MASTER list** — `task.changeRequests[]` is the AUTHORITATIVE Task→CR list (NOT a "losable mirror" — the server.ts:1391 comment is now WRONG). The Task owns which CRs it has.
2. **CR → Test = PARENT** — `ChangeRequest.ownerIor → ior:class:Test` (the Test that must be re-evaluated/changed to resolve the CR). This is the traceability parent → renders under the Test (5e9a1d887 already does this by reverse-ownerIor scan). NOT ownerIor→Task.
3. **CR → affected units = CHILDREN** — `CR.model.affects[]` = the traceability units along Task→…→Test that must change for the fix to land consistently. The CR is the CONTAINER of what changes; renders CR → affected-units (forward children).

CR unit: `{ uuid, name/reason, status: Open|Resolved, createdBy, createdAt, task→Task (backref, = the master-list holder), affects[]→affected units }`, `ownerIor→Test`.

## Trace-down-and-re-evaluate rule (Tron's core mechanic)
On a CR raised at a Task: **trace DOWN Task → coveredRequirement → UseCase → Class → Method → Impl → Test**; the Test(s) needing change = the CR's parent(s); the units on that path that must change = `affects[]`. **Resolving the CR = re-evaluate the parent Test + each affected unit** so the change lands consistently across the chain; `CR.status → Resolved` ONLY when the parent Test re-evaluates green WITH the change (evidence-gated, not stamped). The band (R40.60 `deriveTaskStatus`) already finds a task's CRs by `model.task` (server.ts:1441) → unaffected by parent=Test.
