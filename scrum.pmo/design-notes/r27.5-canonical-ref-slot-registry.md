# R27.5 — Canonical Ref-Slot Registry (design)

**Author:** robbin-architect · 2026-07-01. PO-endorsed. The correct-by-construction fix for the R27.4 slot-misses (ownerIor + Test.methods) AND the 2207 audit walk-gaps — ONE registry so migrations, `trace:audit`, and repair-reasserts all scan the SAME complete slot set. Slot-miss becomes impossible by construction. Folds in the R27.5 audit-calibration.

## The principle
Every place a unit-uuid can live is declared ONCE in `REF_SLOTS[unitType] = { forward[], back[], cross[] }`. No migration/audit/repair hand-lists slots again — they import the registry. `CANONICAL_FORWARD` (today's reachability walk) becomes a DERIVED subset: `forward` only. This is *pin-correctness-explicitly*: an explicit reviewed allow-list, never a name-heuristic ("any uuid-shaped field").

## CRITICAL distinction the data forced (measured across the whole graph)
A uuid-shaped field is NOT automatically a graph edge. Empirically there are THREE kinds — the registry must classify each, because miscategorizing floods the audit with false dangling OR misses real edges:
- **SELF / EXCLUDE:** `uuid` (the unit's own id).
- **TOKEN / EXTERNAL-ID — EXCLUDE (uuid-shaped but NOT unit refs):** `ownerToken`, `uploaderToken`, `deviceId`, `token`, `ownerToken`. Evidence they're not edges: Device.`ownerToken` DEAD:195/195, File.`uploaderToken` DEAD:71, Room.`ownerToken` DEAD:30 — they "never resolve" because they're auth tokens, not units. Including them = ~500 false dangling.
- **GRAPH EDGE — INCLUDE (unit→unit), even when the field name isn't `ior`:** e.g. `testUuid` (TestCase→Test, 1023 live), `roomUuid` (File→Room, DEAD:8 = real dangling), `parent`, `@ownerIor`. Name ≠ kind — classify by "does the value denote a scenario UNIT".

## Two AUDIT AXES (both fold into trace:audit:strict — endorsed by PO)
### Axis 1 — REF INTEGRITY (dangling), via the registry
- **`trace:audit`:** dangling scan = for every unit, every slot in `REF_SLOTS[type].{forward,back,cross}` must resolve (excluding token/self). Reachability walk = seed Requirement **AND Sprint** roots, traverse `forward` only. This alone drops 2207 → the true residual (Test▸testCases + Sprint-roots fix the ~1400 walk-gap; the token-exclusion drops the ~500 false). What remains = real dangling debt (e.g. Method`implementation` DEAD:51, Test`parent` DEAD:32, Test`verifies` DEAD:12) — surfaced honestly for a repair pass.

### Axis 2 — NODE WELL-FORMEDNESS (malformed nodes) — NEW (R27.7 corruption)
Ref-integrity is BLIND to a node that exists-but-is-malformed (the R27.7 `undefined.scenario.json`: a bash-artifact dropped `model.uuid`, so the unit had correct content + a correct parent ref but sat at the wrong path with no id). Derive-checks follow refs and never see it → latent corruption. `trace:audit:strict` HARD-FAILS on (all = 0):
- **missing/undefined `model.uuid`** — every unit must have one.
- **filename ≠ uuid** — basename must equal `<model.uuid>.scenario.json` (instant `grep undefined.scenario.json` check for the bash-artifact class).
- **shard-path ≠ uuid shard** — the 5-char shard dirs must derive from the uuid.
- **duplicate uuid** across files (a mint collision).
This is a DISTINCT axis from ref-integrity — a graph can have 0 dangling refs and still harbor a malformed node. Cheap, and it makes the silently-unwritten-uuid class fail CI by construction.

### Axis 3 — ONE CLASS PER CODE FILE (by-FILE dedup) — NEW (R27.3 synthetic-class sprawl)
The R27.2 reuse-by-name guard dedupes Class units by `model.name` — so N Class units for ONE code file under DIFFERENT synthetic names slip through `duplicateClasses=0`. Real case (R27.3): `scripts/generate-sprint-md.ts` is function-based (0 real classes) yet had THREE Class units — `SprintViewGenerator`, `SprintMdGenerator`, and my premature `GenerateSprintMd` — all pointing at the same file, all passing the name-guard. `trace:audit:strict` HARD-FAILS when **>1 Class unit shares the same non-empty `sourceFile`/`file`** (a function-module or a class-file → ONE canonical Class unit; genuine multi-class files are the rare exception — allowlist explicitly if ever needed). Fix at mint time too: `mintOrReuseClass` should reuse by (name OR sourceFile), not name alone — reusing on sourceFile makes synthetic-sprawl impossible by construction.
**ALLOWLIST (explicit, PO-accepted):** `src/ts/server/server.ts` is a genuine multi-concern MONOLITH (ProxyFetch / Device / JoinRequestFlow / SvgViewer / ServerTUI / core) — >1 Class per file is legitimate here. It is an explicit Axis-3 allowlist entry, NOT a violation. The allowlist is a named list in the audit (per-file, with a reason), so the exception is visible + reviewed, not silent. TRACKED: recommend eventually SPLITTING server.ts into per-concern files (proxy-fetch.ts already extracted; server-tui.ts / device.ts / join-flow.ts next), after which its allowlist entry retires and one-class-per-file holds by default again. An allowlist entry is a debt marker, not a permanent waiver. Three axes together — ref-integrity (dangling) + node-well-formedness (malformed) + one-class-per-file (sprawl) — make the graph's structural invariants a build gate.

### Axis 4 — EVERY [impl:uuid] MARKER HAS A LIVE CHAIN (code-ships-chain-less) — NEW (recurring retroactive #126)
The #126 gap keeps recurring: code ships, then the scenario chain is backfilled retroactively — **4 cases and counting** (R26.6 federation-import, R27.1 statusChecklist, R27.3 per-task-MD, R29.1 self-heal). The by-construction fix (req's standing-PDCA idea → escalated to PO): `trace:audit:strict` scans the CODEBASE for `[impl:uuid:<u>]` markers and HARD-FAILS if any `<u>` (a) has no `Implementation` unit, or (b) that Impl is not reachable from a `Requirement` via the forward chain (Req→UC→Class→Method→Impl). Conversely flag NEW source functions that ship without a marker (heuristic: an exported fn / a diff-added fn in a chain-tracked file with no `[impl:uuid]` nearby). Effect: a PR that ships a `[impl:uuid]`-less impl — or a marker with no requirement behind it — goes RED. That turns "chain-less shipped code" from a repeated manual catch into a build gate — the same correct-by-construction move as R27.2's mint-guard, one level up (the marker, not the Class). Pairs with the reverse direction already covered: orphan-Impl (Impl with no owning Method) is Axis-1/ref-integrity; this is Impl-with-no-Requirement-root. Four axes now: ref-integrity + well-formedness + one-class-per-file + marker-has-chain.

**Detect vs enforce = TWO ACs within R27.5 (PO ruling: one home, no double-ownership; R29.2 folded in + superseded):**
- **AC-marker-chain-detect** — the DETECTION logic (single-source audit: scan code `[impl:uuid]` markers, resolve each to an Impl reachable from a Requirement). This is Axis-4 above.
- **AC-chain-gate-enforce** — the ENFORCEMENT: a DELTA-SCOPED pre-commit + CI block that REUSES the detection — NEW chain-less impls FAIL, the legacy backlog is deferred (delta-vs-absolute, so it doesn't red-fail on the existing 4-retroactive debt). Hook shape: `trace:audit:strict --since=<ref>` scopes to the diff's new markers.
No duplicate audit logic (AC-single-source): the detect AC produces the verdict, the enforce AC blocks the delta. (Originally split as R29.2; PO ruled ONE home = R27.5, R29.2 retired → superseded-by-R27.5 tombstone.)
- **Migrations/repairs (R27.4-style):** repoint over `REF_SLOTS[type]` (ALL edges, fwd+back+cross) — so `Test.methods`/`@ownerIor` back-edges are never missed. The gate = "0 dead refs across all REF_SLOTS", not per-touched-slot.
- **Post-apply reassert:** iterate REF_SLOTS — and per the circular-tool lesson, at least one verifier runs an INDEPENDENT tool over the same registry (not the migration's own report-mode).
