# R30.4 — Lobby member-name regression: resolve from the LOADED profile

**Author:** robbin-architect 2026-07-13 (diagnose+design; req mints scenario-first). Symptom: the lobby "Your Name" field shows a random `User <NNN>` that changes on every reload instead of the user's real profile name.

## Root cause (MEASURED — refines the relayed diagnosis)
`RoomBrowser.ts:29` computes `memberName` SYNCHRONOUSLY at construction:
`params.get('name') || client.getProfile()?.name || localStorage['rawbin-name'] || 'User <rand>'`
— at construction the async profile has not loaded, so `getProfile()` is `null`.

There IS already a self-heal (RoomBrowser.ts:33-42), but it subscribes **only to `MSG.PROFILE_UPDATED`** — an *explicit* profile edit (e.g. vCard import + save). The **initial** profile load is delivered as **`MSG.PROFILE`**, not `PROFILE_UPDATED`:
- `RawBinClient.ts:131` stores `_profile` on `MSG.PROFILE` **or** `MSG.PROFILE_UPDATED`.
- `RawBinClient.ts:140` `emit(msg.type, msg)` forwards **every** message type to `.on()` subscribers — so a `MSG.PROFILE` handler WOULD fire.

RoomBrowser never subscribes to `MSG.PROFILE`, so on reload the loaded profile never re-resolves `memberName`; it stays stuck at the line-29 fallback. `localStorage['rawbin-name']` is written **only** inside the `PROFILE_UPDATED` handler (line 37), so a user who never triggered an explicit update has empty localStorage → **random every reload**. That is the regression.

## Fix (design)
1. **Factor** the self-heal body (set `memberName`, persist `localStorage`, update `#member-name` input, update `rb-avatar name`) into one private method **`applyProfileName(name: string)`**.
2. **Subscribe to BOTH** `MSG.PROFILE` (initial load) **and** `MSG.PROFILE_UPDATED` (later edits); each handler calls `applyProfileName(msg.profile?.name)` guarded on a truthy name.
3. The line-29 **random fallback stays ONLY as last resort** (no profile exists at all); it now self-heals the instant `MSG.PROFILE` arrives.

**Both orderings covered:** profile-arrives-before-construct → line 29 `getProfile()` already non-null (correct name); profile-arrives-after-construct → the `MSG.PROFILE` subscription re-resolves it. DOM update is safe pre- or post-render: `memberName` is always set, and the `#member-name` input / `rb-avatar` are updated only if already rendered (otherwise the next `render()` uses the corrected `memberName` at line 73/70). Idempotent: same name re-applied is a no-op.
