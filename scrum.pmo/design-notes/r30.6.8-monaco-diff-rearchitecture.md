# R30.6.8 — IntelliJ-grade 3-way merge: spike A vs B → recommend CM5 MergeView + node-diff3

**Author:** robbin-architect 2026-07-13 (DESIGN-ONLY; req = sole minter, S30 backlog, TRON-authorized). Quality bar: IntelliJ 3-way merge — LEFT=local | CENTER=result (starts as base-aware auto-merge, editable, autocomplete) | RIGHT=remote; per-change accept-left/right + reject; "Apply All Non-Conflicting"; sync-scroll.

## The defining feature (Tron): BASE-AWARENESS = diff3
IntelliJ uses the common-ancestor **BASE** to auto-apply **non-conflicting** changes (one side touched a region) and flag only **true conflicts** (both sides touched the same region). That IS the **diff3** algorithm. Our in-house LCS has none of it; **CM5 MergeView alone is NOT base-aware** (diffs center↔left and center↔right independently). Base-awareness is the non-negotiable — both options below must supply it.

## Marketplace research (folded in)
IntelliJ-style 3-way merge extensions exist — **VibeMerge** (IntelliJ-inspired), **zawys/vscode-as-git-mergetool** (open-source), Weld/Meld-port, and VS Code's **built-in merge editor** — but **all are VS-Code-API-bound**, none embeddable standalone in a browser app. Studying **zawys** confirms the pattern: it *orchestrates the platform's own editors* (opens the 3 panes, navigates git conflict markers) rather than shipping a portable widget — i.e. it leans on the VS Code runtime. Takeaway: to embed the *real* VS Code merge editor you must bring its runtime (@codingame/monaco-vscode-api); otherwise you assemble the model yourself (CM5 + diff3).

### Recommendation: (B) CM5 MergeView + node-diff3
Delivers the base-aware IntelliJ **model** (the magic Tron wants) lightweight + embeddable, without re-platforming Monaco. (A) only if Tron demands pixel-exact VS Code fidelity and accepts the heavy re-platform + bundle. **Tron picks fidelity vs weight.**

## Design for (B) — the recommended path
- **node-diff3 computes the smart center:** `diff3Merge(local, base, remote)` → merged text with non-conflicting changes **auto-applied** + **conflict regions** marked. That text becomes CM5 MergeView's editable `value` (center).
- **CM5 MergeView renders the 3-pane:** `MergeView(el, { value: smartCenter, origLeft: local, orig: remote, connect: 'align', highlightDifferences: true, revertButtons: true, collapseIdentical: true })` → left+right reference panes, editable center, **copy-across arrows** for remaining conflict resolution, **sync-scroll + row-align**.
- **BASE input** = `GitApi.mergeBase(leftRef, rightRef)` → `git merge-base` (read-only, execFile array-args + ref allowlist, same as GitApi).
- **★ No-base fallback (Tron's ask):** if inputs have **no common base** — comparing the working file vs an arbitrary ref, unrelated histories, or two non-git files (`git merge-base` empty) — **skip diff3** and fall back to **CM5 MergeView's native 2-way copy-across** (center starts as local; user copies across manually; no auto-merge). Graceful degradation, not an error. Base-aware auto-merge engages only when a merge-base exists.

## AC sketch
- Two git refs → `git merge-base` → diff3 auto-merges non-conflicting into the center; conflicts flagged; copy-across resolves them; save writes center.
- No common base (working file vs ref / non-git) → CM5 2-way copy-across, center=local, no auto-merge (documented fallback).
- 3-pane sync-scroll + row-align; center editable; CM5 lazy-loads; coexists with Monaco; GitApi/RepoRegistry feed local/remote (incl OOSH repo, file@ref).
- `computeMergedCenter` unit test: `diff3Merge(local, base, remote)` auto-applies non-conflicting + flags true conflicts (pure, DOM-free).
