# R30.9 — IntelliJ-faithful 3-way merge (custom: Monaco 3-pane + node-diff3 + IntelliJ gutter)

**Author:** robbin-architect 2026-07-13 (DESIGN-ONLY; req = sole minter, S30). **TRON RULING: "IntelliJ 3-way at ANY overhead cost" — max fidelity to IntelliJ *specifically*, weight/effort no object.** Criterion = IntelliJ fidelity, NOT bundle size.

## Why (C) custom, not (A) monaco-vscode-api
The bar is **IntelliJ**, and IntelliJ's merge UX is specific: **LEFT = local (yours) | CENTER = result (editable, fully-functional, autocomplete) | RIGHT = remote (theirs)**; per-change **gutter accept-left ◄ / accept-right ►** arrows; **base-aware** auto-apply of non-conflicting changes; **"Apply All Non-Conflicting Changes"**; synchronized scroll.
- **(A) @codingame/monaco-vscode-api** = the *real VS Code* merge editor (Current/Incoming/Result, checkbox conflict UX). Max fidelity to **VS Code**, but **NOT IntelliJ** — different layout, different interaction. Also a heavy re-platform of our AMD Monaco. → **fails the IntelliJ-specific criterion.**
- **(C) Custom** = we control the UX exactly → we can reproduce IntelliJ's left/result/right + accept-arrows + base-aware + autocomplete center. Cost is irrelevant per Tron. → **truest to IntelliJ. RECOMMEND.**

(CM5 MergeView — the prior lightweight pick — is copy-across + not-base-aware + CodeMirror-not-Monaco (no autocomplete center); good when weight mattered, but Tron removed that constraint and it is not IntelliJ-faithful. Superseded.)

## Design (C) — the IntelliJ-faithful build (Class RbDiffEditor 18165081 REUSE)
### Layout — 3 Monaco editors (IntelliJ left/result/right)
`mountThreePane`: three Monaco editors via a shared `monacoLoader` (reuse the one already loaded by rb-code-editor) — **LEFT** local (read-only), **CENTER** result (read-write, full Monaco = autocomplete/lint/keybindings = IntelliJ's "fully-functional center"), **RIGHT** remote (read-only). IntelliJ column order.

### Base-aware merge — node-diff3
`computeMergedCenter`: `diff3Merge(local, base, remote)` → the CENTER **starts as the base-aware auto-merge** (every non-conflicting change from either side already applied) + a list of **true conflict regions** (both sides changed the same span). This IS IntelliJ's model. **BASE = `GitApi.mergeBase(leftRef, rightRef)`** (`git merge-base`, read-only execFile + allowlist). Pure/DOM-free → unit-testable.

### IntelliJ gutter — accept arrows per change
`renderMergeGutter`: in the gutters between LEFT↔CENTER and CENTER↔RIGHT, render per-change **accept-left ◄ / accept-right ►** arrows (and reject on conflicts), using Monaco decorations + a gutter overlay aligned to the diff3 change ranges. Non-conflicting changes render subtly (already applied); true conflicts highlighted for resolution. Matches IntelliJ's gutter.

### Actions
- `acceptChange(changeId, side)` — apply that side's chunk into CENTER at the aligned range (the ◄/► action). (Re-scopes the old `takeHunk`, now base-aware + IntelliJ-styled.)
- `applyAllNonConflicting` — IntelliJ's "Apply All Non-Conflicting Changes" (diff3 pre-applies them; this (re)confirms/applies any remaining trivial ones).
- `syncScroll3` — synchronized scroll + row-alignment across the 3 Monaco editors.
- `save` (KEEP) — write CENTER via `/api/files` (mtime-guard).

### No-base fallback
If `git merge-base` is empty (unrelated histories / working-file vs arbitrary ref / non-git): diff3 can't run base-aware → fall back to a **2-way** view (CENTER starts as local; accept-arrows still work as plain take-over, no auto-merge). Documented degradation; the IntelliJ base-aware path engages whenever a merge-base exists (the git-version-merge case Tron targets).

## Reference & hardening — VS Code mergeEditor algorithm (MIT), study don't embed
**VS Code issue #37350** (the origin of VS Code's merge editor) confirms the C-custom pick: the requestor asked for *exactly* IntelliJ's layout (LEFT Local | CENTER Result | RIGHT Server), but VS Code shipped its **own** UX (Current/Incoming/Result + checkbox) — VS Code's merge editor is deliberately **not** IntelliJ. So embedding it (option A / monaco-vscode-api) would wear the wrong UX; **C wears the IntelliJ UX.**

**ASSET:** VS Code's merge editor is open-source (**MIT**, Henning Dieterichs / hediet — `vscode/src/vs/workbench/contrib/mergeEditor`). For R30.9, **study its ALGORITHM as reference** (do NOT embed — leverage the proven logic, wear the IntelliJ UX):
- **base-aware diff3 conflict-detection** — how it classifies each change region as auto-mergeable vs a true conflict from the base (validate our `computeMergedCenter`/node-diff3 output against its model).
- **3-pane mapping & accept-region logic** — how a change region maps across base/local/remote and how "accept region" writes into the result (informs `renderMergeGutter`/`acceptChange`).
- **Fold hardening into the node-diff3 integration** (the edge cases a from-scratch LCS/naive diff3 miss): overlapping/adjacent conflict regions (coalescing), **whitespace** handling (optional ignore-whitespace like IntelliJ), **line-ending** normalization (CRLF↔LF so EOL diffs don't spuriously conflict), empty-side / one-side-deletes-region cases, and trailing-newline handling.

This makes the custom build **robust** (VS-Code-proven algorithm) **without the monaco-vscode-api weight**. Scope: this is build-guidance for the `computeMergedCenter` Impl (+ `renderMergeGutter`/`acceptChange`) — **the R30.9 chain (methods/UCs) is unchanged**; no re-mint.
