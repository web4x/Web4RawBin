# R25.2 — WebItem Design (unified URL/bookmark scenario unit)

**Author:** robbin-architect · 2026-06-30. Design-ahead (req captures formal reqs + slug; this note is slug-agnostic — relocate into the canonical sprint dir on creation). Grounded in: existing `ior:class:File` unit, current `.url`/`text/uri-list` handling (content-preview.ts), and the OOSH `webitem` script (`components/OOSH/dev/webitem`).

**Key grounding:** the OOSH `webitem` script ALREADY names the Web4 target format `*.webitem.scenario.json` (line 26) and ships `create <name> <url>` + `webloc2json` / `webloc2url` / `webloc2xml` converters. R25.2 makes that scenario unit real and wires the Web4 side to the same converters.

## ior:class:WebItem
```jsonc
{
  "ior": "ior:class:WebItem",
  "model": {
    "uuid": "<v4>",
    "kind": "link" | "folder",          // discriminator (folder has children, no url)
    "name": "Cerulean Circle",
    "description": "",
    "url": "https://cerulean.circle/...", // link only; null for folder
    "scheme": "https",                    // derived from url protocol
    "icon": "https://www.google.com/s2/favicons?domain=cerulean.circle",  // favicon
    "badge": "🔒",                        // scheme emoji (https🔒 http🌐 ftp📁 mailto✉ file📄)
    "parentFolder": "ior:instance:<folder|room>",  // nav parent (back-ref, NOT a chain edge)
    "children": [ "ior:instance:<WebItem>", ... ]  // FOLDER ONLY — forward array (folder→children)
  },
  "ownerIor": "ior:instance:<room or parent folder>"
}
```

## (1) WebItem vs File — PARALLEL classes, WebItem OWNS urls
Different ontology: **File IS-A stored byte artifact** (contentHash/contentPath/size — the bytes ARE the value); **WebItem IS-A reference to an external resource** (the value is remote; no meaningful local payload). So:
- **WebItem REPLACES** the bare `text/uri-list` File-with-url-bytes storage **for URLs** (Tron's wording). A dropped `.url`/`.webloc`/`.desktop` or pasted URL → mint a **WebItem**, NOT a File.
- **File stays** for real byte content (images/docs/audio). Not replaced.
- **Drop-router decision:** by type — uri-list / .url / .webloc / .desktop / bare-URL-text → WebItem; everything else → File. (Single dispatch point, mirrors the fillPreviewPane mime-dispatch DRY.)
- **Migration:** existing File units whose mimeType=`text/uri-list` (or name endsWith .url/.webloc) → convert to WebItem (extract url from the stored bytes, mint WebItem, repoint room child, retire the File unit). One-shot migrator script.

## (2) Folder hierarchy — children[] forward, parentFolder nav
Bookmark tree = WebItem folders containing WebItems (recursively):
- **Folder** WebItem: `kind:"folder"`, `children:[ior...]` (forward array), `url:null`.
- **Link** WebItem: `kind:"link"`, `url` set, `children` absent/empty.
- `parentFolder` = nav back-ref (folder IOR, or the room for top-level) — same role as `ownerIor`/`Profile.parent`; NOT a chain edge. Forward truth = the parent's `children[]` (mirrors File-tree / Profile.companies[] / Class.methods[] forward-array discipline).
- "What's in this folder" = read `children[]`; "where does this live" = `parentFolder`. Reverse ("who links here") = walk — no back-pointer beyond parentFolder.
- Root bookmarks = WebItems with `parentFolder` = room (`ownerIor` = room).

## (3) Import — .url / .webloc / .desktop / Google bookmarks
Reuse/mirror the OOSH `webitem` converters; each importer mints WebItem(s) + wires children/parentFolder:
- **.url (Windows):** INI `[InternetShortcut]` → `URL=<url>` line. → one link WebItem.
- **.webloc (macOS):** plist XML → `<key>URL</key><string>…</string>`. (OOSH `webloc2json` already does this — emit `.webitem.scenario.json`.) → one link WebItem.
- **.desktop (Linux):** `[Desktop Entry]` → `URL=`. → one link WebItem.
- **Google bookmarks (Netscape HTML):** nested `<DL>` with `<DT><H3>folder</H3>` + `<DT><A HREF="url">name</A>`. → **full TREE**: `<H3>` → folder WebItem, `<A HREF>` → link WebItem, nesting → children[]/parentFolder. This is where the folder hierarchy is populated en masse.
- **Derived fields on mint:** `scheme` ← url protocol; `badge` ← scheme→emoji map; `icon` ← `https://www.google.com/s2/favicons?domain=<host>` (or `<origin>/favicon.ico` fallback); `name` ← `<A>` text / `.url` filename / `<title>`.

## (4) OOSH webitem script pattern → Web4 mapping
The OOSH `webitem` script is the cross-platform converter (create + webloc2{json,url,xml}). Map it forward, consistent with the **S24 Object.verb skill** discipline:
- `webitem.webloc2json` should emit a `*.webitem.scenario.json` matching `ior:class:WebItem` above (the format it already names).
- Web4 side = a **`WebItem` Object.verb skill class** (so it's introspectable / Tab-completable / emitted, per S24): verbs `WebItem.create <name> <url>`, `WebItem.importWebloc <file>`, `WebItem.importUrl <file>`, `WebItem.importDesktop <file>`, `WebItem.importGoogleBookmarks <html>`, `WebItem.tree <?folder>`, `WebItem.toWebloc`/`toUrl` (round-trip out to native formats). Same registry/emit/CI-drift pattern as Chain/Pin (S24).
- **Preview reuse (R23.2):** a WebItem whose url is YouTube → the embed renderer already built; generic url → iframe/best-effort. WebItem.icon/badge render in the file browser + detail.
- **Round-trip:** WebItem ↔ .webloc/.url/.desktop via the converters → import on drop, export on download (the New-tab/download action resolves `url`).

## Gaps / decisions to flag
1. **kind discriminator vs duck-typing:** recommend explicit `kind:"link"|"folder"` (clear, gateable) over inferring from url/children presence.
2. **Migration is destructive-ish:** converting legacy text/uri-list File → WebItem retires File units — gate it (dry-run + count, like the company dedup migration). Don't silently drop.
3. **favicon fetch = external call** (google s2 favicons / remote favicon.ico) — privacy/offline note; store the icon URL (lazy-load) rather than fetching+embedding bytes, OR cache as an artifact. Decision for PO/Tron.
4. **Where WebItem lives in the chain:** it's a room artifact (like File), nav-parented to room/folder — not a 6-step-chain node itself; its FORMALIZATION (the skill) is the chain-tracked work.
