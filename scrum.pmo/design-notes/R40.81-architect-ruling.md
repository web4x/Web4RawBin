## Q1 — mof-m1 gains `project:model` under scenario-index → **(a) REGRESSION. Scope the resolver. NOT a baseline update.**

**Verdict: FIX. The resolver must scope model-tree reads (mof-m1 aggregation) to model-tree units, so reading from scenario/index is byte-identical to reading from model-store.**

Why (a) not (b):
1. **The Slice-2 contract is behavior-transparency.** PAIR-2 exists to prove the read-source repoint changes NOTHING a user sees. It changed something (a new top-level `project:model`). That is a failed repoint *by definition* — independent of whether the new node is desirable. A silent behavior change riding in on an infrastructure repoint is wrong even if the change were nice; desirable additions get their own req + AC + sanctioned baseline, never a free rider.
2. **model-store was correctly SCOPED, not incomplete.** The 786-unit model-store enforced model-tree scope IMPLICITLY by physical exclusion. scenario/index (6825, the FULL store incl native-scenario reqs/tasks/tests) does not. Collapsing stores REMOVED the implicit scope filter → the render aggregates over units it never used to → synthesises `project:model`. `project:model` is a DERIVED aggregation node (PO: no stored file anywhere) over the full store's **native-scenario content** (the scenario framework's own units) — scenario-system internals, out of the USER model-tree's scope by design. Two independent measures agree (tester: "native-scenario M1 units"; PO: derived-node over 6825 not 786).
3. **Root cause = implicit scope must become explicit on store-unification** (my standing structural doctrine). The store boundary was doing scope-filtering by accident. Unifying the physical store is fine; the LOGICAL model-tree scope must be re-established EXPLICITLY in the resolver (an `isModelUnit` scope on the mof-m1 aggregation), never left as an artifact of which folder a unit sits in.

**Fix:** the read resolver, when serving the model tree, scopes its unit set to model-tree units (`isModelUnit`) regardless of physical backing store. scenario/index stays the physical backing; the model-tree view resolves the SAME logical set as the old model-store. Expected post-fix PAIR-2: 213/213 byte-identical, **mof-m1 3 == 3**, no `project:model`.

**NOT a 213-baseline update.** Do not sanction `project:model` as an accepted delta. If `project:model` in /model is ever genuinely wanted, that is a DELIBERATE separate feature (own req + AC + explicit baseline change), not a rider on this repoint.

**Bindings upheld:** RED = STOP holds. data/model-store STAYS until PAIR-2 is green on the fix commit. Default stays model-store (nothing flips for Tron). Slice-3 stays blocked. Tester re-runs PAIR-2 ONCE, on the fix commit only (not a re-run of the current RED — that standing order stands).

## Q2 — server.ts:2948-2949 prod→store FALLBACK read inside the add-view WRITE handler → **EXEMPT from the read-view resolver; couple it to the WRITE store.**

**Verdict: EXEMPT — it is a WRITE-PATH validation read, and a validation read must resolve from the SAME store its paired WRITE targets, NOT from the read-view resolver.**

Reasoning: routing this read through `resolveReadDir` would DESYNCHRONISE it — under `MODEL_READ_SOURCE=scenario-index` it would validate against scenario-index while the add-view WRITE still lands on MODEL_STORE (writes are Slice-3) → validate-here / write-there = a NEW split-brain, worse than leaving it. A validation read is write-coherence, not view-coherence; it is legitimately NOT a `resolveReadDir` (PAIR-2 view) site. The read-view single-source (expert's "0 `? MODEL_STORE :` read-forks remain") is about VIEW reads; this is a different category and does not violate it.

**Do:** leave it on the WRITE store (MODEL_STORE) now; in **Slice-3 it moves WITH the writes** (stays coupled to the write store, never to the read flag). Add a label at the site so a future grep does not mistake it for a stray read-fork: `// write-path validation read — tracks WRITE store, moves in Slice-3; NOT a resolveReadDir view site`. Tripwire: if this read ever feeds a user-visible VIEW, re-audit (then it becomes a PAIR-2 site).
