# R40.81 Slice-3 — WRITE/READ STORE COUPLING (architect design, 2026-09-06)

PO-routed from 0.0 (my Q2 finding). Design-only → hand to expert. Prevents the validate/write split-brain that opens when the default store flips to scenario-index while writes still target model-store. Backstops: PAIR-2 GREEN @a4e2a2511 endorsed (fix = measured scope discriminator, real transparency, matches pre-stated 213/213 + mof-m1 3==3).

## The hazard (why coupling, precisely)
Today: read-store is chosen by the `MODEL_READ_SOURCE` flag (`modelReadDir()` reads it at call time); write-store is hardwired to MODEL_STORE (`data/model-store`), including the add-view validation read at server.ts:2948-2949 (labelled write-path). While the flag defaults to model-store, reads and writes agree — no split-brain. The moment the default flips to scenario-index, **reads resolve scenario-index, writes resolve model-store → the two stores diverge** (new writes land only in model-store; reads from scenario-index never see them). That is the split-brain. A repair-migration touching Tron's live data must make this **impossible by construction**, not "two call sites that currently agree."

## The coupling — ONE object owns which store (radical OOP)
Introduce a SINGLE owner of the store-dir decision for a model unit — the only place that (a) decides is-this-a-model-unit and (b) reads the store-source flag. Both reads and writes obtain their dir from it; nothing else chooses a store.

```
class ModelStoreLocator {           // the single source of "which physical store backs this model unit"
  dirFor(uuid): string              // is-model-unit? + which-store (reads the ONE flag) -> the dir
}
```
- **READ path:** `resolveReadDir(uuid)` → `locator.dirFor(uuid)` (replaces the current isModelUnit-ternary + `modelReadDir()`).
- **WRITE path:** the unit write (UnitController put) AND the server.ts:2948-2949 validation read → `locator.dirFor(uuid)`.
- **Consequence:** for any given uuid, read and write resolve the SAME dir because they call the SAME method. Flipping the flag flips BOTH atomically. There is no second store-choice that could disagree → split-brain is **unrepresentable**, not merely avoided.

**Rename the flag `MODEL_READ_SOURCE` → `MODEL_STORE_SOURCE`.** After coupling it governs reads AND writes; a name that says "READ" invites a future dev to add a write path that ignores it (re-opening the split). The name must assert the truth (it selects the STORE). Measure blast radius of the rename first (grep the flag name; it's env + a few reads) — identifier change, small, but do it deliberately.

## Guard — by-construction, scan the HAZARD not the actors
A lint asserting the store choice has exactly ONE owner:
- **0 occurrences** of a model-store dir literal (`data/model-store` / the model dir) OR a `MODEL_STORE_SOURCE` read **outside `ModelStoreLocator`**. The hazard names itself (a store-dir chosen elsewhere); the scan is unevadable and needs no discovery mechanism.
- **stub-must-fail BITE:** add a second store-choice (a stray dir literal or flag read in a handler) → lint RED. A guard that can't bite is decorative.
- This subsumes the expert's "0 `? MODEL_STORE :` read-fork" into the stronger invariant: 0 store-choices anywhere but the locator (reads AND writes).

## ★ Risk I must name — rollback semantics change once WRITES flip
"model-store STAYS as rollback" (PO step 5) is a CLEAN rollback ONLY within the window before writes diverge. Once the flag flips and writes go to scenario-index, model-store stops receiving writes → it is a **point-in-time snapshot, not a live mirror**; a rollback (flip back) after any post-flip write LOSES those writes (model-store never got them). Two ways to handle — a reversibility-vs-simplicity call for PO/Tron, decide BEFORE the flip:
- **(a) DUAL-WRITE bake window:** the locator writes to BOTH stores during a bounded bake window (reads from the flagged one). Rollback stays clean the whole window; remove dual-write at confidence. Still single-owner (one object writing two dirs, NOT two call sites). Recommended if clean reversibility matters.
- **(b) BOUNDED point-in-time rollback:** accept model-store as a snapshot; keep the bake window SHORT + monitored; NAME the accepted risk (rollback after the window loses post-flip writes). Simpler, weaker reversibility.

## Sequence — I AGREE with the PO's 6 steps, with 2 additions
1. **COUPLE the write path FIRST** (the single `ModelStoreLocator`, both paths through it) — ✓ correct: the guard must exist before the flip enables the hazard. *Addition:* couple = the single-owner locator (by construction), not "make the validation read track the write store" (that's convention).
