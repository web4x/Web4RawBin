## THE SPINE — gate-by-construction (the property, not the invocation)
The AC to design toward is NOT "the gate is invoked" but **"a deploy performed the NORMAL way CANNOT complete un-gated."** Mechanism: the scripted deploy's exit-0 path is *structurally gated* — the ONLY way `runScripted` returns success is for `DeviceGateTrigger.runAndRecord` (R40.25) to have returned GREEN as its final step. No branch reaches exit 0 without it; there is no skip flag to reach around it.

## CHAIN (3 UCs + the fold-in) — recommend ONE cohesive Class `Deployer` (scripts/deploy.mjs), 3 methods
(R27.2 one-Class-per-code-class: if all 3 live in one deploy module → one Class; req splits only if sourceFiles genuinely diverge, e.g. an always-on monitor daemon.)

### UC-1 `deploy.runScripted` → Class `Deployer` → Method `Deployer.runScripted` → Impl
The ONE command. Sequence (fail-loud + atomic at every step): **build** → **commit** (build atomically with deploy) → **restart DETACHED** (start.mjs blocks on the foreground server → the restart must be spawned detached / nohup so the sequence isn't swallowed) → **wait served==committed** (rides R30.28 `assertVersionAtHead`; poll with timeout, LOUD on timeout) → **`DeviceGateTrigger.runAndRecord`** (R40.25, gate:device:live @390 real-WebKit) → **record + report** → **exit NON-ZERO on gate RED or NOT-RUN**.

### UC-2 `deploy.monitorDrift` → Class `Deployer` → Method `Deployer.monitorDrift` → Impl
Ongoing served≠committed drift detection AFTER ship (distinct from R30.28's ship-time one-shot). Re-checks served==committed==SW==HEAD on demand/interval; on drift → LOUD alert + non-zero. The COMPARISON rides `b6946e59.assertVersionAtHead`; the monitor loop + alert is new.

### UC-3 `deploy.pinTopology` → Class `Deployer` → Method `Deployer.assertPinned` → Impl
Pin the deployment topology as a unit/config (host, port, node version=node22, the prod server pane) and assert the live deploy matches it (right host:port, node22 ABI, correct pane). Distinct from R30.28 (version=WHAT) — topology=WHERE/HOW.

`runScripted`'s final step INVOKES R40.25's `DeviceGateTrigger.runAndRecord`. The INVOCATION-as-final-step is R31.14's property (INV-D1); the gate Method/Impl are R40.25's units — **reference/invoke, do NOT re-mint** (verify-owner-first; DeviceGateTrigger Class is R40.25's to mint against scripts/post-deploy-gate.mjs).

## INVARIANTS
- **INV-D1 gate-by-construction — ENFORCED (behavioural bite + STATIC lint, PO 2026-08-10):** `runScripted` has NO exit-0 path that skips `runAndRecord` GREEN — the gate is the terminal step, structurally unavoidable.
  - *Behavioural* (META-BITE #1): a normal deploy cannot complete un-gated (EXPECTED-RED until ship). Catches the paths that EXIST.
  - *Static lint (the upgrade — prevents paths that don't exist YET):* assert that in the deploy script EVERY exit-0 / success-return is **downstream of** the `DeviceGateTrigger.runAndRecord`-GREEN check — no early success path before the gate returns GREEN. Enforceable form: `runScripted` has EXACTLY ONE success-exit and it is guarded by the gate result; any additional `process.exit(0)`/success-return, or one not dominated by the gate-GREEN branch, → RED. This converts INV-D1 from "we tested the paths we thought of" to "a new bypass path cannot be ADDED without the check going RED" — same upgrade as the facet-type lint (the second source can't reappear).
  - *Two-bite (per standard):* (i) plant a bypass `exit(0)` before the gate in a fixture → lint RED; (ii) meta-assert the LINT ITSELF RUNS → weaken/remove it and the suite goes RED. Behavioural bite = paths that exist; static lint = paths that don't exist yet.
- **INV-D2 no DISHONEST bypass — but an HONEST owner-recorded override EXISTS (PO 2026-08-11):** there is NO `--skip-gate`/`--force`/silent bypass flag (a gate an agent must remember has reliability = that agent's memory = how S23's gate never ran). BUT a blocking gate with NO legitimate escape hatch WILL be disabled (precedent: someone silently removed `check:task-status` from ci:gates to green CI). So the pressure-release is provided as HONEST DATA, not withheld — see the OWNER-RECORDED OVERRIDE below. The distinction: a bypass hides that the gate didn't pass; the override RECORDS it, owner-gated, and stays visibly RED.
- **INV-D3 atomic + fail-loud:** any step fails → LOUD error + NO partial state; a partial deploy is worse than a refused one. Never half-deploy.
- **INV-D4 exactly-ONE-deploy-path (when done):** two paths = the two-sources disease and one would be the ungated one. Retire the old manual restart ONLY after runScripted has succeeded ≥1 live.
- **INV-D5 dry-run-first + safe rollout:** `--dry-run` proven first; the EXISTING working restart path STAYS as the fallback until the scripted path has succeeded at least once (no big-bang cutover).
- **INV-D6 served==committed rides R30.28:** the comparison is `b6946e59.assertVersionAtHead`, not a second copy (single-source; do not re-derive served/committed).

## ★ OWNER-RECORDED OVERRIDE — the honest pressure-release (PO required, before build)
Principle: **NOT-RUN == FAILURE == RED — a gate not known-GREEN is RED.** The gate outcome is DATA on the deploy/gate unit (R40.25 `DeviceGateTrigger.runAndRecord`), never a log, version-stamped. The override makes the inevitable escape hatch HONEST instead of leaving only the dishonest one (commenting out the trigger).

- **(a) DISTINGUISH the two REDs** — `runAndRecord` records `gateStatus`:
  - `GREEN` (ran, passed) · `RED_FAILED` (ran, tests failed) · `RED_INFRA` (could NOT run — WebKit cannot-launch, which genuinely happened this campaign) · `RED_OVERRIDDEN` (see b). All non-GREEN BLOCK exit-0 by default, but `RED_FAILED` vs `RED_INFRA` need different diagnosis (a real regression vs an infra outage), so they are recorded distinctly. A deploy with **NO gateStatus at all** = the trigger was bypassed = the worst RED (see d).
- **(b) OVERRIDE = owner-gated + recorded as DATA (R40.10 `approvedBy` shape):** an override writes `deployedWithGateRed: true, overriddenBy: <ownerTok8>, overriddenAt: <iso>, overrideReason: <text>, overRedKind: RED_FAILED|RED_INFRA` onto the deploy/gate unit. Owner-gated exactly like `TaskQaVerdict.approveByOwner` (only the owner can, evidence-precondition). Provable FROM THE RECORD, never remembered. `runScripted` exit-0 requires **GREEN OR a valid recorded override** — nothing else.
- **(c) an overridden deploy stays VISIBLY UN-VERIFIED + audited:** gate-status renders `RED-OVERRIDDEN` (never GREEN) — the deploy is honestly marked un-verified. It MUST appear in the R37.5 honest-status audit (an overridden deploy is a KNOWN debt) so it cannot ROT: it stays on the audit list until a clean gate goes GREEN and clears it. Same fail-visible principle — silence can't impersonate a green deploy.
- **(d) removing/bypassing the trigger without a recorded override = the gate-removal offence, DETECTABLE:** (i) the static lint (INV-D1) already requires every exit-0 downstream of the gate; EXTEND it: the deploy path MUST contain the `runAndRecord` invocation — its ABSENCE fails the lint (a deploy script without the trigger call → RED). (ii) runtime: a deploy that completed with **no gateStatus record** is invalid/flagged (the trigger didn't run) — an unrecorded deploy cannot masquerade as gated. So both a compile-time (lint) and a data-time (missing record) net catch a silently-removed trigger. Two-bite as usual: plant a trigger-removed deploy script → lint RED; weaken the lint → suite RED.

**INV-D7 not-run==red:** any gateStatus ∈ {absent, RED_FAILED, RED_INFRA} blocks exit-0 unless a valid recorded override is present; there is no GREEN-by-default.
**INV-D8 override-is-data-not-memory:** exit-0 on RED requires the `deployedWithGateRed`+by+at+reason record (owner-gated); an override asserted in prose/commit-msg but absent from the unit does NOT satisfy it.
**INV-D9 overridden-stays-red-and-audited:** an overridden deploy renders RED-OVERRIDDEN and appears in the R37.5 audit until a GREEN gate clears it — it never reads GREEN and never silently ages out.

## GATE (tester, distinct #126 Tests — no cross-wire onto R30.28)
- **META-BITE #1 (the key one):** attempt a deploy with the gate step removed/short-circuited → the deploy MUST fail non-zero (cannot complete un-gated). Currently RED (a deploy can complete un-gated) → GREEN when the by-construction gating ships. Plus a self-presence bite: weaken the gating so a skip is possible → suite RED.
- runScripted: build→commit→detached-restart→served==committed→gate→exit-code all proven in `--dry-run`; NO skip flag exists (grep-lint).
- monitorDrift: inject a served≠committed state → LOUD + non-zero; clean state → pass.
- assertPinned: mutate host/port/node → fails; matching topology → pass.
- Prod-safety: dry-run leaves prod untouched; old restart path still works until first live success.
