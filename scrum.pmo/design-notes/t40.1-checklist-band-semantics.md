# T40.1 CHECKLIST↔BAND semantics — architect ruling (2026-08-29, Tron IMG_5174)

Tron-facing (his surface, T40.1 7a956c21). State model = my ruling. Single-status-writer stands: status is DERIVED from the checklist, NEVER authored.

## DIAGNOSIS (measured, first-hand) — the band is HONEST; the CHECKLIST is wrong
- The band `QA-Review-with-open-CR` derives PURELY from `hasOpenCrSubstep(checklist)` (task-status.ts:43: `if best!==Done && hasOpenCrSubstep(checklist) → band`). It reads the OPEN processing-CR sub-step IN the checklist — **NOT a parallel flag.** So the band is not a second source; it derives from the checklist.
- The DEFECT: the served decline flow does `reopen:true` (server.ts:1653 `UnitController.apply(..., {reopen:true, addChangeRequest})`) → TaskPolicy UNTICKS QA Review (task-policy.ts:49-51, "untick QA Review/Done → deriveStatusEnum derives In Progress"). So after a decline: QA Review **[ ]** + processing-CR **[ ]**. That is exactly what Tron sees.
- His R40.59 AC (verbatim): "a decline must NOT regress to In Progress — **QA Review stays [x]** + NEW sub-step Processing Change Requests [ ] → Done." **The served decline UNTICKS QA Review, violating his AC.** The band is correct (open sub-step → band); the QA-Review box is wrong (unticked by the reopen).

## INTENDED SEMANTICS (checklist = the SINGLE source; band DERIVES; no parallel flag; no direct status write)
- **CR OPENED (decline):** QA Review **STAYS [x]** (do NOT reopen-untick) + insert `Processing Change Requests [ ]`. ⇒ deriveStatusEnum top = QA Review; band = open sub-step ⇒ `QA-Review-with-open-CR`. Tron sees **QA Review [x] + Processing Change Requests [ ]** = "in QA Review, processing CRs" (his mental model: "the task state IS in processing CRs").
- **CR APPROVED (not the last open one):** sub-step stays `[ ]` (still processing); QA Review stays `[x]`.
- **CR DECLINED (another, while already banded):** adds a CR; sub-step stays `[ ]`; QA Review stays `[x]`.
- **LAST open CR RESOLVED (the approval/resolution that clears the final open CR):** tick `Processing Change Requests [x]` ⇒ `hasOpenCrSubstep` false ⇒ band CLEARS ⇒ deriveStatusEnum = QA Review (clean) ⇒ Tron re-judges → Done.
- **INVARIANT throughout:** QA Review NEVER unticks (no regress to In Progress); status DERIVED from the checklist; the band = `hasOpenCrSubstep` (pure derivation from the sub-step); opening/resolving CRs **WRITES the checklist** (insert/tick the sub-step), never a parallel flag, never a direct `m.status`.

## FIX (served sub-step model — makes his board honest NOW; no direct status write)
1. **Decline:** REMOVE the QA-Review-untick — the decline must NOT `reopen`-untick QA Review; keep QA Review `[x]` + `insertOpenCrSubstep`. (deriveStatusEnum then reads QA Review [x] top; band layers on the open sub-step.)
2. **Approve (per-CR, his 2nd complaint "approve moved nothing"):** when the approval resolves the LAST open CR (all the task's CR-children approved), **tick the processing-CR sub-step [x]** ⇒ band clears. Non-last approve → leave `[ ]`. The approve WRITES the checklist (tick the sub-step); the band DERIVES (hasOpenCrSubstep). The CR-children state is the TRIGGER; the checklist is the SOURCE the band reads — not a parallel flag.
