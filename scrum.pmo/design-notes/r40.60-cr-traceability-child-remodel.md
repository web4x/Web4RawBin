# R40.60 — CR = traceability child + per-CR approval (mechanics design, 2026-08-25)

## Tron's shape (verbatim), mechanized
1. **CR is a TRACEABILITY CHILD of the TASK** (same shape as Requirement) — NOT a `changeRequests[]` string list, NOT a checklist sub-step.
2. **EACH CR individually approved AT the task** — owner-gated (his QA judgment), per-CR.
3. **Band derives from ANY-CR-not-approved** — clears ONLY when EVERY CR individually approved, never one tick.
4. **NO bulk accept-all** — retire `resolveCr`.

## (1) CR UNIT = traceability child of the Task (mirrors Requirement)
- New `ior:class:ChangeRequest` unit: `{ uuid, title/description, approvedBy, approvedAt, ownerIor→Task, crossRef→contestsTest }`.
- **Parent = the TASK** (`ownerIor → Task`), exactly like a Requirement is the task's traceability child. The task lists its CR children the same way it covers Requirements (a child-ref array on the task, or CR.ownerIor→Task resolved as children — mirror the Requirement pattern, coveredRequirements-style).
- ★ CR-PARENT TENSION RULED (req's question): per THIS ruling the CR's traceability PARENT = the TASK (not the Test, as #86's 4babebb1 ownerIor→Test had it). Keep `contestsTest` as a **crossRef** (the CR contests a Test, but its traceability parent is the Task). ownerIor→Task; crossRef→Test.
- RETIRE the `m.changeRequests` STRING array (task-policy.ts:142) — CRs are units, not strings.

## (2) Per-CR individual approval (owner-gated, Tron's QA)
- A **per-CR approve** action AT the task sets `CR.approvedBy/approvedAt` on ONE CR unit — owner-gated by the EXISTING owner mechanism (I do NOT touch owner-auth; that surface is Tron's/closed). His QA judgment, one CR at a time.
- No auto-approve, no bulk. Each CR is approved on its own merit.

## (3) Band RE-SOURCED to CR-children-approval (single-source preserved)
- TODAY the band = `hasOpenCrSubstep(checklist)` (a sub-step). RE-SOURCE it: band = **∃ CR-child of the task with `!approvedBy`**.
- deriveStatusEnum stays the PURE checklist primitive (Planned/In-Progress/QA-Review/Done). The BAND becomes a **task-level derived status** composing checklist + CR-children — **ONE function `deriveTaskStatus(task, crChildren)`** (mirrors rollupParentStatus): `if deriveStatusEnum(checklist) === 'QA Review' AND hasUnapprovedCr(crChildren) → 'QA-Review-with-open-CR'; else deriveStatusEnum(checklist)`. `hasUnapprovedCr = crChildren.some(c => !c.approvedBy)`.
- ★ SINGLE-SOURCE (the whole arc's law): `deriveTaskStatus` is the ONE band definition site; EVERY band-consumer (approve-gate, current-eligibility, scoreboard, pin, drawer) reads deriveTaskStatus — NO parallel band derivation. RETIRE `hasOpenCrSubstep` + `PROCESSING_CR_SUBSTEP` as the band source.
- **Clears iff EVERY CR approved** — `hasUnapprovedCr` false only when all CR children have approvedBy. One CR still unapproved → band persists (Tron's "never one tick").

## (4) NO bulk accept-all — RETIRE resolveCr
- RETIRE the sub-step resolve (`task-policy.ts:99-104`, `subStep === PROCESSING_CR_SUBSTEP`) AND `server.ts:1658` resolveCr. The per-CR approve (2) replaces it; there is NO action that clears the band in one step. Grep-guard: `PROCESSING_CR_SUBSTEP`/`resolveCr` appear in NO live path.

## Decline flow (cleaner than #86 — no untick+substep atomic pair)
- A decline **mints a CR-child (unapproved)** on the task → `deriveTaskStatus` derives the band from it. NO untick-to-In-Progress, NO checklist sub-step. The band IS the QA-Review-with-open-CR state, current-able, not-Done-able. (The R40.59 atomic-untick+substep invariant is MOOT — replaced by mint-CR-child → derived band.)

## Preserved R40.59 invariants (re-sourced, not dropped)
- Band **current-able** (unchanged). Band **∉ APPROVE_STATUSES** → task Done gated on band-cleared (ALL CRs approved) AND task QA-approved. Done-with-open-CR impossible by construction.

## Migration (gated)
- Existing `m.changeRequests[]` string entries + any `processing change requests` sub-step → MINT `ChangeRequest` units (ownerIor→Task, unapproved). Gated dry-run+COUNT (CRs minted == existing entries; INV no-CR-lost). Then retire the sub-step + hasOpenCrSubstep + resolveCr. Reversible.

## Failable gate (stub-must-fail, the arc's discipline)
- band derives from CR-children: a task with ≥1 unapproved CR-child → band (RED if it clears without ALL approved); ALL approved → clears. **Stub:** one CR unapproved → band MUST hold (green-if-clears = RED). NO bulk-clear exists (resolveCr gone — grep = 0 live). Per-CR approve owner-gated (non-owner per-CR approve → 403). Single-source: no band derivation outside deriveTaskStatus (RED on a 2nd site).
