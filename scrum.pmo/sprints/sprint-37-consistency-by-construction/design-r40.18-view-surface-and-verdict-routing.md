## ★ TIMESTAMP (Tron RULED: add it) — `current = MOST-RECENTLY-ADVANCED In-Progress` + WIP=N
Final predicate: **current = the In-Progress task with the MAX `lastAdvancedAt`** (single, deterministic, DERIVED at render, never stored — R40.17); the pin ALSO surfaces WIP=N so parallel In-Progress work stays visible.
- ★★ **SEAM-WRITTEN, never by callers (PO's hard constraint — the whole point):** `TaskPolicy.apply`/`UnitController` stamps `lastAdvancedAt = now` as a CONSEQUENCE of the advance, in the SAME atomic write — exactly like emit-as-consequence-of-mutating. A caller CANNOT set it (it's not an accepted intent field). The binding lint (no mutation outside the seam) covers it FOR FREE: a task can't advance without the seam, the seam always stamps → omission-proof BY CONSTRUCTION. If a caller could advance without stamping, we'd have re-created omission-by-default ONE FIELD LOWER (the exact reason the pin is stale today) — so binding it is non-negotiable.
- **Q1 — what counts as an ADVANCE: a status TRANSITION *OR* a `statusChecklist` sub-step change (tick/untick). BOTH stamp** (PO's lean, agreed): in-progress work is expressed by sub-step ticks, not just status flips — 37.24 sat In-Progress while real work ticked INSIDE it, so the last sub-step is the truer "what am I working on" than the last status change.
- **Q2 — ABSENCE (every existing task has none): untimestamped ranks LAST, never first, never silently wins.** BACKFILL **S37 NOW from GIT** (each task unit's last status/checklist-changing COMMIT time = its real historical advance — small, ~27 tasks, and it's the sprint Tron watches, so the pin is correct THERE immediately). ★ **LABEL THE PROVENANCE (PO refinement):** a git-derived stamp is the time the advance was RECORDED, not necessarily when it HAPPENED — so a backfilled value MUST be marked distinct from a live seam stamp (`lastAdvancedAtSource: 'git-backfill'` + the commit hash it came from, vs `'seam'` for live). Otherwise in three weeks a reader treats an approximation as a live measurement — the same class as a stale banner or a fork-lie stamp (cheap to label now, unrecoverable later). The predicate ranks on `lastAdvancedAt` regardless of source (best-available advance time); the SOURCE field is honesty metadata, read by humans/audits, never by the ranking. Other sprints = untimestamped, ranked-last, stamped by the seam on their next advance, tracked by a **SELF-DRAINING debt gate** (report-only: emits each ci run the count of In-Progress tasks lacking `lastAdvancedAt`, auto-clears as the seam stamps them — NOT a silent defer, the R40.4 lesson). Edge: if ALL In-Progress are untimestamped (pre-backfill) → the predicate falls to the honest WIP=N set (no arbitrary single).
- **Q3 — field location: ON the Task unit (`model.lastAdvancedAt`), NOT a side-index.** It is atomic with the seam's status/checklist write (one write, no cross-store drift a side-index (R36.2c) would add). ★ It is **RECENCY METADATA, NOT status** — the predicate reads it for RANKING only; **nothing derives status from it** (guard: the no-2nd-source lint asserts `deriveStatusEnum`/status never reads `lastAdvancedAt`; status stays sourced from `statusChecklist` alone). So it is not a 2nd source of truth about status.
- **Tester:** the gate asserts the pin VALUE = the In-Progress task with the max `lastAdvancedAt` (and WIP=N reflects the count); stub-must-fail = a Planned/untimestamped task must NEVER be named current.

## RULING 3 — Task-verdict sites (approveByOwner / declineToChangeRequest) → DEFERRED-TO-T37.4.3 + tripwire
Measured (expert): `approveByOwner` writes `m.approvedBy`/`m.approvedAt` + `m.status='Done'` LITERALLY; `declineToChangeRequest` writes `m.changeRequests` + `m.status='In Progress'` LITERALLY. Routing via apply is therefore NOT byte-identical (checklist-tick+derived ≠ literal 'Done', evidence fields dropped) = a BEHAVIOR MIGRATION, not slice-1's INV-T==0 mechanical route; and NOT exemptable (a Task status change is exactly what has live views). Belongs to existing **task-37.4.3 (`3b8f21c6`)** — "controller is the UNIQUE DOMINATOR of any unit mutation; single-source Done delegation, R40.10 approve DELEGATES".
**END-STATE RULING (T37.4.3 design, mine): YES — `TaskPolicy.apply` gains an evidence-data-merge path; approve/decline become `transition(target) + data-intent`:**
- The transition TICKS the checklist item → `deriveStatusEnum` DERIVES the status; the evidence data (`approvedBy`/`approvedAt` / `changeRequests`) merges as intent. The literal `status=` write is REPLACED by the derivation.
- ★ **NON-NEGOTIABLE (R40.10 — Done STAYS Tron's act):** approve is a DELEGATION of Tron's verdict, NEVER a derived completion that can impersonate it. Enforced by construction: (a) `deriveStatusEnum` stays the SOLE status writer — the evidence-data-merge intent must NOT accept `status` as a field (no literal-status back door through the intent bag; MvcBoundaryGuard still forbids it); (b) the approve transition is Tron-GATED + fail-closed — it fires ONLY on his actual approve act, and the checklist item it ticks IS the "Tron approved" evidence, so `deriveStatusEnum` reaches Done ONLY when that Tron-evidence item is ticked (derivation reflects his verdict, never invents it); (c) the agent/skill status endpoint **REFUSES Done** (the PO bound) — an agent may advance to In Progress/QA Review, never Done; only Tron's approve delegation reaches Done.
- This CHANGES BYTES (checklist-derived ≠ literal) = a BEHAVIOR migration = **its own item (T37.4.3), after slice-1** — the 2 sites deferred + tripwire, not slice-1 mechanical. Expert's read confirmed.
