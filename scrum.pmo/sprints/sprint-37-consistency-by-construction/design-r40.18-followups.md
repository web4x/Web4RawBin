## FOLLOW-UP 1 — the advance signal is BIASED: paperwork > building
★ **The bias (real, measured on 37.24):** `lastAdvancedAt` stamps on a status transition OR a checklist sub-step tick — both are CHECKLIST EDITS (paperwork). Writing CODE does NOT stamp it. So 37.24 (last checklist edit @11:18) ranked BEHIND 37.25 (@11:32) while 37.24 was the task actually being BUILT (routing + R40.18 emit). "Most recently advanced" therefore systematically favours paperwork over building — the opposite of "what am I working on."
**DESIGN: count code as a first-class advance — `lastAdvancedAt` effective = MAX(checklist-advance, code-advance).**
- **Code-advance = a commit touching the task's MARKED DECLARATION** — NOT the whole file (PO over-credit caveat, adopted). Attribute to the `[impl:uuid]`-marked method's code, exactly as chain credit does (AST-attach, not file-presence): `git log -1 --format=%cI -L :<methodName>:<sourceFile>` follows THAT declaration's code history, so a drive-by edit to another function in the same file (e.g. an unrelated task also touching unit-controller.ts) does NOT bump it. Narrower attachment = less it can lie (same discipline as the no-2nd-source lint). ★ RESIDUAL NAMED: where `-L` can't scope a declaration (method moved/renamed across files, generated/bundled output, multi-file method) → fall back to file-level for that task AND label the provenance `source='code-file'` (vs `'code-decl'`) so the over-credit possibility is visible, never silent. Multi-Impl task → max over all its marked declarations.
  - ★★ **SPECIFIC RESIDUAL (PO, NOT theoretical) + MECHANICAL TRIGGER:** `unit-controller.ts` is now THE choke-point EVERY routed task touches, and 37.24's Impl (`apply`) is `source='code-file'` (couldn't -L-scope the TS static method). So file-level attribution there will **over-credit 37.24 as soon as ANOTHER task commits code to the controller for its own reasons** — a spurious bump making the pin silently point at finished work. **RESIDUAL** = "a pin winner attributed `source=code-file` on the SHARED seam file can be a spurious bump from a different task's work" (file-level over-credit is worst on SHARED/choke-point files — touched by all tasks — and best on task-specific files). **TRIGGER** = the FIRST observed case where 37.24 wins on `source=code-file` while the touching commit belongs to a DIFFERENT task — and the LABEL makes that case DETECTABLE (L16 feeding L10: the provenance label is not just honesty, it is the trigger's detection signal), so the revisit is MECHANICAL, not someone-remembering. **Fold into the live-code-stamp follow-up**, which should prioritize `code-decl` precision for the SHARED-file declarations (`apply`/`create` in unit-controller.ts) first — those are where file-level lies most.
- **Live (by-construction, symmetric with the checklist stamp):** a commit-time step (the CI/deploy pass already processes commits) resolves each touched `[impl:uuid]` → its owning Task (Impl.ownerIor→Method→Class→UC→Req; Task covers the Req) and stamps that task's `lastAdvancedAt = commit-time, source='code'` THROUGH THE SEAM → it emits → the pin re-derives live on a CODE commit. So Tron watches the pin move as the actual BUILDING happens, not just when a box is ticked.
- **Backfill parallel:** the git-backfill maxes-in the last-commit-touching-the-Impl-sourceFile (source='code') alongside the last-status/checklist-change commit — historical building counts too.
- **Provenance:** `source` ∈ {`seam` (live checklist), `code` (commit touching the Impl), `git-backfill` (historical)} — honesty-labeled, ranked-not-status (L15/recency-not-status guard extends).
- Removes the bias: building and paperwork BOTH advance the pin. Impl→Task resolution (multi-hop via the chain) is the one impl-detail; a commit touching N Impls stamps all N owning tasks.
- ★ **SPLIT — what lands NOW vs follow-up (RULED for the re-run):** the **BACKFILL code-recency lands in THIS re-run** — `lastAdvancedAt = MAX(last status/checklist-change commit, last commit touching the task's Impl sourceFile)` — because it is what makes **37.24 win by GENUINE recency** (its Impl `e3729f51` files committed TODAY > 37.25@11:32), NOT by reconcile-ORDER; it dissolves the 37.24-vs-37.27 coin-flip and satisfies the PO's caveat-2. It is CHEAP (the re-run already does a git-log per task; add the Impl-sourceFile git-log + max). The **LIVE code-stamp (commit-time hook stamping the owning task through the seam on a code commit) is the DEFERRED follow-up** (the by-construction live mechanism — design, not this deploy). So: backfill +code-recency now (robust genuine-recency, removes the reconcile-order fragility); live code-stamp later.
- ★ **DEFERRAL RESIDUAL + TRIGGER NAMED (L-deferral, not a silent "phase 2"):** RESIDUAL = until the live hook lands, a CODE commit does NOT move the pin in realtime — only checklist edits (seam-stamped) push live; code-recency is captured only at the NEXT backfill run. So a task actively being CODED shows as most-recently-advanced only after its next checklist edit OR the next backfill, NOT the moment its code commits. (The pin is still CORRECT after a backfill; it just isn't live on a bare code commit until the hook exists.) TRIGGER = fold the live code-stamp in with the SKILL-ENDPOINT work (the UDS agent-write channel) — that pass already adds commit-time/agent-originated writes through the seam, so the code-stamp is a natural rider; if that work slips, a standalone tracked req. Named + triggered, not silently phase-2'd. The re-run reports per-task PROVENANCE (WHY 37.24 wins: its code committed today, not that it was reconciled last).
- ★ **RECONCILE PLAN SIMPLIFIES (PO's question): YES — write-ORDER no longer carries the truth.** With code-recency in the re-run, 37.24 wins STRUCTURALLY (its marked-declaration code is the freshest), so the ascending-genuine-advancement WRITE-ORDER workaround becomes UNNECESSARY — the ordering is IRRELEVANT (a mechanism, not a human-performed sequence). Reconcile each of the 7 to TRUTH in ANY order; 37.24 wins by its code regardless. Belt-and-braces (keep the order) is harmless but not required. Structural > procedural — the coin-flip dissolves instead of being carefully avoided.

## FOLLOW-UP 2 — R37.5 sub-step-checked / parent-unchecked sweep (bounded: 7 tasks measured)
★ **Root:** a checklist with an In-Progress SUB-step checked (`  - [x] refinement`) but the PARENT `- [ ] In Progress` UNCHECKED — you can't do a sub-step of a phase without being IN that phase, so the checklist is internally inconsistent, and `deriveStatusEnum` (keys on the parent) yields Planned. Measured extent: **7 tasks** of 515 (37.24, 37.27, task-31.6, task-98, task-184, task-142, iframe-pinch) — small, tractable.
**DESIGN:**
- **Extend R37.5 `assertStatusConsistent`:** flag "any sub-step of phase X checked ⇒ phase X parent must be checked" (internal-checklist-consistency, a distinct axis from the existing status-vs-statusChecklist reconcile).
- **Reconcile PER-TASK TO TRUTH, never uniformly (R37.5 no-status-invention):** where the sub-step GENUINELY happened, check the parent (37.24 → In Progress, implementing done); where it did NOT, UNcheck the sub-step (correct DOWN) — do not invent an In-Progress a task never entered.
- **Phased + gated report-only→strict (self-draining):** the gate EMITS the count of internally-inconsistent tasks each ci run (start 7) and auto-flips strict at 0 — the counter is the revisit trigger, no silent defer.
- **Tracked follow-up (its own req), NOT this deploy.** The 37.24/37.27 reconcile for THIS deploy is the first 2 of the 7 (req's lane, ascending genuine-advancement order per the PO); the other 5 drain via the gate.

## FOLLOW-UP 4 — LIVE-ON-ADVANCE BOUNDARY (the seam-vs-file-edit trap) — DESIGN, capture-only (Tron schedules)
The pin updates live for SEAM-routed advances (statusNext → UnitController.apply → emit) but NOT for a bare agent FILE-EDIT — honest, but a TRAP: agents edit files by habit, and a file-edit to a task's status makes EVERY live view (pin, board, tree) stale, not just the pin (family-not-instance). ★ BY-CONSTRUCTION ANSWER = BOTH (not either/or, declared-not-defaulted):
- **The sanctioned WRITE PATH** — agent task-status/checklist writes route THROUGH the seam via the UDS/skill endpoint (already designed) → emit → live. The positive path.
- **A GATE that FLAGS an out-of-seam task status/checklist edit** (extend the mutation-seam lint family / a status-drift detector: a task whose status/statusChecklist changed without a corresponding seam write is a flagged BYPASS). The negative enforcement — the bypass is DETECTABLE, never a silent stale-view. Declared-not-defaulted: a file-edit-status-write is a named bypass, not a silent non-live.
- **REJECT a server `fs.watch` bridge** (auto-emit on external file change): it's a SECOND emit trigger alongside the seam = the two-source risk we keep killing, plus debounce/write-then-commit-race hazards. The endpoint+gate is the clean single-source answer.
- Neither half alone: the endpoint doesn't STOP the file-edit habit (the gate flags it → corrects toward the endpoint); the gate alone flags but gives no live path. Family = ALL task-status writes / ALL live views, not just the pin. Capture-only; Tron schedules.
