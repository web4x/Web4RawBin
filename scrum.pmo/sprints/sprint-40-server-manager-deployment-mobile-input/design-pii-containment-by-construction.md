### Options

- **(a′) STAGED challenge-response MIGRATION → ★ RECOMMEND.** Generalize R40.22 dual-validity from owner-only to ALL entities: (1) **accept-both** (raw token + new device-key/session) — nobody locked out; (2) **per-client enroll+prove** a device-key/session (79 keypair-Devices + 42 ssh-Rooms immediate; 116 raw-only Devices + 1 User enroll during the window, bootstrapped by their still-valid raw token); (3) **disable raw-token PER-CLIENT after that client proves the new path** (prove-before-kill, per-entity NOT global). ### ★ TOKEN_REDIRECT usability (PO's crux question — VERIFIED in code, not reasoned)
The client stores `m.newToken` on `TOKEN_REDIRECT` (server.ts:3232/3293). Two server issue-sites:
- **`server.ts:3731` (IDENTIFY) — issued on BARE TOKEN presentation** (`redirectTombstoneToPrimary(token)`, `authMethod='token'`, NO second factor). ⇒ **an attacker holding a leaked token hits IDENTIFY and receives the SAME redirect** → rotation-via-this-path migrates the attacker alongside the victim. It is a token-CONSOLIDATION mechanism, NOT a revocation one.
- **`server.ts:4000` (DEVICE_ENROLL) — issues a devicePrivateKey/keypair** = part of the (a) enrollment migration, gated by the enroll flow (a second factor), NOT a bare-token shortcut.
**Verdict: TOKEN_REDIRECT does NOT make (b) cheap+safe for the raw-only majority.** You cannot securely rotate a shared secret using only that same public secret to authenticate the rotation — the attacker is indistinguishable and follows. TOKEN_REDIRECT securely rotates ONLY entities that already have a second factor (the 79 keypair devices) — which is exactly (a)'s enrollment, not a (b) shortcut.

### Recommendation — TRIAGED HYBRID (I ACCEPT the PO's incident≠endgame framing; I REFUTE "TOKEN_REDIRECT makes (b) cheap" with the evidence above)
The hard truth: **a raw-only entity's ONLY credential is its now-public token — you cannot both keep it working AND evict the attacker** (indistinguishable). So "kill now" for raw-only = invalidate = lockout-until-re-enroll; there is no cheap secure middle. Triage by (second-factor × value × liveness):
1. **NOW, zero-lockout:** repo **PRIVATE** (stops new exposure) + **invalidate the DATA-ownership tokens** (File 186 / WebItem 18 — not interactive clients, no lockout) → removes 204 forge-credentials immediately.
2. **NOW, secure:** rotate **Tron's own devices + the 79 keypair devices** via the device-key-gated path (attacker lacks the key, can't follow). Highest value + securely rotatable; Tron re-enrolls interactively.
3. **Raw-only interactive clients (116 Device + 1 User + 3 Room):** no cheap secure kill exists. DECIDER = **active-vs-stale triage** (last-seen) — most of the 116 are likely abandoned test devices whose invalidation is harmless; invalidate those now, and for genuinely-active ones run the (a′) dual-validity window so they re-enroll before their raw token dies. **Flagged to req/Tron** (liveness + device→owner = PII).
4. **ENDGAME: (a′)** challenge-response migration (by-construction: raw bearer permanently inert). This is the endgame, NOT the incident action — it leaves the raw-only leak live for the window, so it does not substitute for steps 1-3.
**Execute nothing; Tron decides the user-impact tradeoff.** Evidence, not intent: enrollment ratio 79/195 (~40%), 324 raw-only, TOKEN_REDIRECT bare-token-authorized at :3731.

### STEP 2 — secure owner-token rotation for Tron + the 79 keypair devices (device-key-gated, attacker can't follow)
Reuses existing primitives (measured): `verifyChallenge` (server.ts:4014), DEVICE_ENROLL (:3964-4000), `authMethod='device-key'` (:4017), per-client `challenge` (:3490). Per target device:
1. **Mint** a new ownerToken; store BOTH old+new as valid for that entity (dual-validity), `acceptLegacy=true` per-entity.
2. **Prove:** the device signs its per-connection `challenge` with its **device private key**; server `verifyChallenge(newToken, devicePublicKey, challenge, sig)` must pass (`authMethod='device-key'`). An attacker holding the leaked OLD token has NO device-key → cannot pass → cannot obtain/bind the new token.
3. **Kill:** only AFTER the device has authenticated on the NEW token via device-key, flip `acceptLegacy=false` for THAT entity (prove-before-kill, per-entity — NOT global). Old token dead; leaked copy worthless.
4. **Tron first:** rotate Tron's own device(s) interactively (he re-proves via device-key), verify he holds an owner route on the new token BEFORE killing his legacy — his lockout is the worst outcome.
- **Backstop (mine, on land):** dual-validity accepts old+new before any kill; per-entity prove-before-kill holds; boot-check fail-loud; C4-inert re-verified if tree changed; pre/post field-presence — the rotated entities' OLD tokens reach 0-live while non-target (raw-only) entities are untouched (step 3 triage).

## History question — SEQUENCING SETTLED BY TRON (2026-08-11): rotate-first → repo-private → residual-PII history
**★ Tron's chosen order:** (1) **ROTATION** of the 240 `ownerToken`s server-side (RUNNING, R40.22 approved) — neutralizes the leak that history/private cannot reach; (2) **repo private**; (3) the **residual-PII history question** — which DROPS in urgency once the 240 tokens are dead (a leaked name is harm, not access). The PII untrack (Step 2 of the gate) + history rewrite both come AFTER rotation. AFTER rotation, the history question reduces to ORDINARY PII:
- **Making the repo private stops NEW exposure but git HISTORY retains the PII** — every past commit still contains the values (incl. Tron's number). Private ≠ removed.
- **Actual removal from history = a rewrite** (`git-filter-repo` or BFG) purging the PII files/paths from all commits. Consequence: **every commit SHA changes** → all clones must re-clone/re-fork; open PRs/branches break; **anyone who already cloned or forked retains the old history regardless.**
- **The exposed values should be treated as already-public** (a public repo may be cloned/indexed/cached by third parties). A phone number isn't "rotatable" like a token — that is a real-world decision for Tron.
- **Options for Tron:** (a) private + leave history (fast; stops new exposure; history + existing clones still hold PII); (b) private + history rewrite (purges repo history; SHAs change; forks/clones still hold it); (c) accept exposure + rotate whatever is rotatable. **The rewrite is Tron's call; we lay out consequences and do not execute.**
