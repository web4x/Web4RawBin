# Cross-view role AGREEMENT — architect design (2026-08-24, Tron rejected R40.56 at his surface)

Tron's screenshot (record aa3fa299): the pin reads "📌 Current — Task 40.1" while THAT task's drawer still offers "📌 Set as Current." Two views on ONE screen disagree about a derived role. Design-only, req mints. Independent of the tester's 3-cause discrimination — valuable whichever cause.

## ★ THE REFRAMING (PO, load-bearing): single-source ≠ correct-source — it means EVERY CONSUMER AGREES
R40.56 deleted the second *derivation* and proved the RESOLVER returns the designation. **True and insufficient.** A consumer can read the correct resolver and STILL render a contradiction if its own COPY of the result is stale. Our gate asserted the SOURCE; Tron's eye asserted the AGREEMENT — and the eye was the stronger test. New gate CLASS: **consumer-vs-consumer on the rendered artifact**, not consumer-vs-model. [[assert-the-rendered-artifact-not-a-proxy]]

## MEASURED root (first-hand) — two COPIES at different freshness
- **pin/tree** `rb-trace-tree.ts:107` subscribes `ViewBus.subscribe(viewBusKey({type:'CurrentSprint', uuid:singleton}), …)` → on a live make-current it RE-DERIVES. **Fresh.**
- **action-bar** `rb-detail-drawer.ts:498` reads `rModel.pinRole` — a field BAKED into the served task payload at fetch time (`attachTaskPinRole`, server.ts:2901, on the /api/ior GET). The drawer does NOT subscribe to the currentsprint broadcast, so a pin-move never refreshes its `pinRole`. **Stale.**
- ⇒ make-current on Task 40.1: tree badge updates live → "current"; the drawer's already-rendered `pinRole` still says "other" → still offers Set-as-Current. R40.56's source-fix can't help: both compute from `slots.current`, but the drawer computed ITS copy at a stale moment. **The disagreement is a lifecycle gap, not a derivation gap.**

## RULING — the by-construction fix: NO SECOND COPY + derive-at-render from ONE live event
Answering the PO's three options:
- **(iii) YES — primary: do NOT ship `pinRole` in the payload at all.** The disagreement is POSSIBLE only because the role is a separate copy with its own lifecycle. A derived ROLE need not be copied — it is a pure function of `(thisTaskUuid, currentSlotUuid)`, and the client already has both live. Remove `pinRole` from the served task model (retire `attachTaskPinRole` as a payload field). No copy ⇒ nothing to go stale ⇒ the class is eliminated, not mitigated.
- **(ii) YES — the mechanism: same broadcast, one event, atomic re-derive.** The drawer subscribes to the SAME `viewBusKey({type:'CurrentSprint', uuid:singleton})` the tree uses (ONE builder both sides — the R37.12 Q3 lesson; a raw-uuid subscribe is exactly why the tree once went stale). On that broadcast AND on render, the drawer derives `taskRole` by comparing its shown task's uuid to the CURRENT current-slot uuid, read from the ONE live current source both views share. Pin-move → one event → BOTH re-derive → **agreement is atomic by construction**: "derived-role and pin-slot change atomically for all consumers" IS the real invariant.
- **(i) fresh-wins on the baked `pinRole` — REJECTED as the wrong shape here.** Fresh-wins (R40-root-#2, status) is the mitigation for data you MUST copy (status CONTENT). A derived role need not be copied at all; keeping the copy + racing to refresh it re-opens the gap on any missed subscription (exactly today's bug). Eliminate the copy (iii), don't manage its freshness.

**Net shape:** the current-slot uuid is the ONE live client-side value (fed by the currentsprint broadcast, read via one accessor); every role-consumer — pin badge, tree highlight, action-bar verbs, scoreboard — derives its role from THAT at render time. No server-baked role field. Single live source + derive-at-render = every consumer agrees because they all read the same live value on the same event.

## ★ MISSING AC — CROSS-VIEW AGREEMENT (the gate Tron's eye is)
**On one rendered screen @390, for the SAME task, the pin/tree role and the action bar's offered verbs MUST agree: `current ⇒ Set-as-Current ABSENT; not-current ⇒ PRESENT`. Asserted by SCREENSHOT, the views checked against EACH OTHER — NOT each against the model.**
- **Why consumer-vs-consumer:** the prior gates (single definition-site, resolver-correct) assert derivation is single-sourced. They CANNOT catch a stale-copy disagreement — both consumers "read the right resolver." Only comparing the RENDERED views to each other catches what Tron saw. This is the distinct gate class the session was missing.
- **DYNAMIC case is mandatory (the bug lives post-broadcast):** render the screen, make-current on a DIFFERENT task via the LIVE path (broadcast, no drawer re-fetch), THEN screenshot → agreement must hold ACROSS the live event. Initial-fetch agreement is trivial and would false-pass; the defect is only visible after a live pin-move.
- **stub-must-fail:** inject a disagreement — a screen where the tree shows `current` but the drawer offers Set-as-Current (i.e. re-bake a stale `pinRole`, or suppress the drawer's broadcast subscription) → the gate MUST RED. A gate that can't be made to fail by injecting a disagreement is not asserting agreement. (This IS the R40.56-defect specimen at the RENDER layer — the strongest baseline.)
- **enumerate-not-universal + fail-closed:** enumerate the role-consumers on a screen (pin badge · tree highlight · action-bar verbs · scoreboard). A NEW role-consumer must be added to the agreement set or the gate flags it (a consumer outside the cross-check can silently disagree — the divergence check). If any enumerated consumer's role can't be read for the comparison, RED — never skip-as-pass.
