# Live-MVC: drawer duplicates + icon stale — ONE root, ONE contract (architect diagnosis, 2026-08-20)

Tron device-QA v0.8.121, verbatim: "hard refresh fixed it, but we want live mvc." The bus DELIVERS immediately (PO corrected: not a propagation failure); the RECEIVE-SIDE render is broken. On ONE event, two views fail two different ways — that contrast is the diagnostic.

## ★ ACCEPTANCE (PO, unambiguous): the LIVE-rendered DOM MUST EQUAL the FRESH-LOADED DOM for the same state.
After the action, NO reload, every view shows the correct state **rendered EXACTLY ONCE**. This one property subsumes all symptoms: duplication (live≠fresh), stale icon (live≠fresh), wrong-current (live≠fresh). **EXPLICITLY NOT acceptance: "a refresh shows it correctly"** — a refresh-only-correct view IS the bug; the reload is only how Tron escaped it. **Do NOT optimise the reload path or add a reload/refetch to the live path** — that is the swallowed-degrade pattern (fail-safe ≠ fail-loud) in a new mask.

## Root-cause (B) duplication + (C) stale icon TOGETHER — the live-update CONTRACT is not uniform
Two views, one event, two failures — both are drift in HOW a view subscribes and WHAT it does on receipt:
- **(C) SUBSCRIBE-KEY DRIFT (measured):** `rb-trace-tree.ts:104` subscribes on the **RAW uuid** `'current-sprint-singleton-0000-000000000001'`, but the broadcast notifies on the **canonical `viewBusKey({type,uuid})`** = `'currentsprint:current-sprint-singleton-…'` (live-bridge.ts:14, ViewBus.ts:19/22). Key mismatch → the pin subscription NEVER fires → icon never re-renders. (Same family as the Q3 key-mismatch: one builder, both sides — this site never adopted it.)
- **(B) RENDER-IDEMPOTENCY DRIFT (measured):** `rb-task-detail.render()` (line 30-53) clears subs + sets base `innerHTML` (good), but its **async tail** — after the `/api/ior` fetch (line 66+) — does `insertAdjacentHTML('beforeend'/'afterend')` to APPEND Parent (78), status-checklist (73), source-link (75), change-requests (100). These async appends are **not guarded against a superseding render**: a live event re-enters render() while an earlier fetch is in flight (or its tail resolves after the reset) → the appends STACK → Parent×2, Status×3. The render is not idempotent — live-DOM ≠ fresh-DOM.
⇒ **ONE root family: the live-update contract.** A view must (1) SUBSCRIBE via the canonical `viewBusKey`, and (2) RE-RENDER idempotently so live==fresh. (C) violates (1); (B) violates (2). Fix the CONTRACT, not the two symptoms (per-view patches = the copy pattern we killed).

## Impl-shape (hand to expert) — built on live==fresh
1. **Canonical subscribe everywhere (fixes C):** `rb-trace-tree.ts:104` → `ViewBus.subscribe(viewBusKey({ type: 'CurrentSprint', uuid: 'current-sprint-singleton-…' }), …)` — the SAME builder the notify uses (ViewBus.ts:19). No raw-uuid subscribe survives.
2. **Idempotent render (fixes B) — FAMILY-WIDE, not rb-task-detail alone.** ★ ENUMERATED (PO: name the family): rb-task-detail is NOT the only one. **~9 `*-detail` components share the exact `render()→async-fetch→insertAdjacentHTML` shape** — `rb-detail-view`(6 inserts), `rb-requirement-detail`, `rb-file-detail`, `rb-test-detail`, `rb-implementation-detail`, `rb-method-detail`, `rb-class-detail`, `rb-usecase-detail`, `rb-task-detail`(4) — PLUS the **shared append-helpers** they all call: `renderChainPathSection` / `renderAllChildrenSection` / `renderSupersededSection` (detail-superseded.ts). Measured: **NO shared base** (each `extends HTMLElement` directly) and **NO generation-guard anywhere** (only the drawer has a ref-guard at rb-detail-drawer:479; the detail BODIES have none). So every one of them duplicates on a live re-render the moment it's open — Tron just happened to have the task detail open.
   - **The fix is ONE shared idempotent-render contract covering ALL of them, not a per-component patch** (that would be the copy pattern one layer down). Two viable shapes: **(a) a `RbDetailBase` base class** every `*-detail` extends, whose render() bumps `this._gen` and whose async tail applies via a shared `applyIfCurrent(gen, fn)` that no-ops if superseded (the R30.25 generation-token pattern, proven); OR **(b)** since there is no base today, a shared `renderGuarded(host, buildAsync)` helper in detail-superseded.ts (already the shared append-home) that ALL detail render()s route their async tail through, AND the shared `renderChainPathSection`/`renderAllChildrenSection`/`renderSupersededSection` take the generation token + no-op when stale. Prefer **build-COMPLETE-then-assign-once** for the async sections where feasible (idempotent by construction); use the generation-token where the two-phase render must stay.
   - Net: one contract, all ~9 components + the shared helpers inherit it. Fixing only rb-task-detail leaves 8 loaded guns.
   - **★ PO SHAPE RULINGS:** (1) **STRUCTURAL OWNERSHIP > opt-in helper** — prefer the `RbDetailBase` that OWNS the render lifecycle so an unguarded tail is NOT EXPRESSIBLE; a `renderGuarded()` helper each component must REMEMBER to call is the reminder-not-mechanism pattern (a 10th component is born unguarded). Helper route acceptable ONLY as tier-2 (detectable-not-impossible) and THEN the lint is MANDATORY (RED on any unguarded async tail anywhere), not advisory. (2) **BUILD-COMPLETE-THEN-ASSIGN-ONCE is preferred wherever feasible** — idempotent BY CONSTRUCTION (no partial appends observable, no token to get wrong, live==fresh falls out); generation-token ONLY where a two-phase render is genuinely unavoidable. (3) **FIX THE SHARED APPEND-HELPERS FIRST** (renderChainPathSection / renderAllChildrenSection / renderSupersededSection in detail-superseded.ts) — all 9 route through them, so making THOSE idempotent covers most duplication in ONE small diff, then the direct per-component inserts. (4) **ONE SHIP COVERING ALL 9 — no partial.** A fix for the one component Tron opened, leaving 8 loaded guns, is worse than a slightly-later complete fix (he re-hits it immediately; 'fixed' credibility is thin). If the full 9 cannot land safely in one ship, expert tells PO BEFORE splitting — PO decides sequencing.
3. **(D) banner string (the lie):** `universal-actions.ts:155` reads `📌 Now current — status ${j.status} (the pin follows the derivation; no stored pin)` — STALE from the reversed R40.44 model. We now DO store an explicit-wins-while-valid designation. Fix to the ACTUAL mechanism, e.g. `📌 Now current — status ${j.status} (you set this current; holds until Done or you set another)`. Remove "no stored pin."

## §DEFECT-#2 EXACT RE-ENTRY PATH (PO's :229 lead, answered by measurement)

On **make-current with the drawer ALREADY OPEN on Task 40.1**, the broadcast fires this subscription → `rb-task-detail.render()` RE-RUNS → its async tail (`insertAdjacentHTML` Parent:78 / statusChecklist:73) APPENDS onto the already-populated DOM → **Parent×2, Status×3**.
