# Live-MVC: drawer duplicates + icon stale — ONE root, ONE contract (architect diagnosis, 2026-08-20)

Tron device-QA v0.8.121, verbatim: "hard refresh fixed it, but we want live mvc." The bus DELIVERS immediately (PO corrected: not a propagation failure); the RECEIVE-SIDE render is broken. On ONE event, two views fail two different ways — that contrast is the diagnostic.

## ★ ACCEPTANCE (PO, unambiguous): the LIVE-rendered DOM MUST EQUAL the FRESH-LOADED DOM for the same state.
After the action, NO reload, every view shows the correct state **rendered EXACTLY ONCE**. This one property subsumes all symptoms: duplication (live≠fresh), stale icon (live≠fresh), wrong-current (live≠fresh). **EXPLICITLY NOT acceptance: "a refresh shows it correctly"** — a refresh-only-correct view IS the bug; the reload is only how Tron escaped it. **Do NOT optimise the reload path or add a reload/refetch to the live path** — that is the swallowed-degrade pattern (fail-safe ≠ fail-loud) in a new mask.

## Root-cause (B) duplication + (C) stale icon TOGETHER — the live-update CONTRACT is not uniform
Two views, one event, two failures — both are drift in HOW a view subscribes and WHAT it does on receipt:
- **(C) SUBSCRIBE-KEY DRIFT (measured):** `rb-trace-tree.ts:104` subscribes on the **RAW uuid** `'current-sprint-singleton-0000-000000000001'`, but the broadcast notifies on the **canonical `viewBusKey({type,uuid})`** = `'currentsprint:current-sprint-singleton-…'` (live-bridge.ts:14, ViewBus.ts:19/22). Key mismatch → the pin subscription NEVER fires → icon never re-renders. (Same family as the Q3 key-mismatch: one builder, both sides — this site never adopted it.)
- **(B) RENDER-IDEMPOTENCY DRIFT (measured):** `rb-task-detail.render()` (line 30-53) clears subs + sets base `innerHTML` (good), but its **async tail** — after the `/api/ior` fetch (line 66+) — does `insertAdjacentHTML('beforeend'/'afterend')` to APPEND Parent (78), status-checklist (73), source-link (75), change-requests (100). These async appends are **not guarded against a superseding render**: a live event re-enters render() while an earlier fetch is in flight (or its tail resolves after the reset) → the appends STACK → Parent×2, Status×3. The render is not idempotent — live-DOM ≠ fresh-DOM.
⇒ **ONE root family: the live-update contract.** A view must (1) SUBSCRIBE via the canonical `viewBusKey`, and (2) RE-RENDER idempotently so live==fresh. (C) violates (1); (B) violates (2). Fix the CONTRACT, not the two symptoms (per-view patches = the copy pattern we killed).

## Impl-shape (hand to expert) — built on live==fresh
1. **Canonical subscribe everywhere (fixes C):** `rb-trace-tree.ts:104` → `ViewBus.subscribe(viewBusKey({ type: 'CurrentSprint', uuid: 'current-sprint-singleton-…' }), …)` — the SAME builder the notify uses (ViewBus.ts:19). No raw-uuid subscribe survives.
2. **Idempotent render (fixes B):** make `rb-task-detail.render()` produce the SAME DOM every call. Preferred: **build the COMPLETE innerHTML (including the async `/api/ior`-derived Parent/Status/source/CR sections) and assign it ONCE** — no post-hoc `insertAdjacentHTML` appends into a live container. If the async fetch must stay, guard it with a **per-render generation token**: bump a counter at render() entry; the async tail applies its result ONLY if its token is still current, else no-ops (a superseded render never appends). Either way: re-entrant render() = one clean DOM, not stacked appends.
3. **(D) banner string (the lie):** `universal-actions.ts:155` reads `📌 Now current — status ${j.status} (the pin follows the derivation; no stored pin)` — STALE from the reversed R40.44 model. We now DO store an explicit-wins-while-valid designation. Fix to the ACTUAL mechanism, e.g. `📌 Now current — status ${j.status} (you set this current; holds until Done or you set another)`. Remove "no stored pin."

## Gate (property, not per-symptom) — the anti-copy guard
- **LIVE==FRESH property test, over the ENUMERATED current-view set (req R37.12):** the current-consuming views are **{ CurrentSprint pin icon, drawer detail, tree-highlight, scoreboard }** — enumerate them explicitly (a view added later without joining the set is itself a finding). Perform make-current with NO reload; snapshot each view's DOM; hard-reload; snapshot again. **ASSERT live-DOM === fresh-DOM for EACH, AND no two current-views disagree** (any two showing a different "current" = RED). One property, all three symptoms, all views.
- **stub-must-fail (two, proving each root bites):** (i) a re-render that appends (non-idempotent) → live has duplicate sections → live≠fresh → RED; (ii) a ViewBus.subscribe on a raw uuid (not viewBusKey'd) → that view doesn't update → live≠fresh → RED.
- **Lint (by-construction, keep it fixed):** every `ViewBus.subscribe(...)` on a unit must go through `viewBusKey(...)` — a raw-string/uuid subscribe key = grep-lint RED (closes the subscribe-key drift for good). Ref the R40.45 "one builder both sides" + the Q3 lesson.
- Do NOT accept a gate that passes on reload — the gate must run WITHOUT a reload on the live path.
