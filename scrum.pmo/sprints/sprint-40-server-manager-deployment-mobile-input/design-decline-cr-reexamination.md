# Decline → Change-Request re-examination (design, impl-shape)

robbin-architect 2026-08-18. Tron: declining T40.1 minted CR `4babebb1` and the app REGRESSED status QA-Review → In Progress, LOSING the QA-Review achievement. Required: **QA Review stays [x]** with a new sub-step **`Processing Change Requests` [ ]** under it → then Done; NEVER a fallback to In Progress. req is minting the requirement; I design the mechanics. **Design only.** Same family as everything today: a GREEN artifact (QA-Review / a passing Test / a satisfied Requirement) must not survive a NEW FACT (the decline/CR) unexamined.

## Measured
- **The regression (server.ts:1629-1631, `declineToChangeRequest`):** after minting the CR it does `m.status = 'In Progress'` (a DIRECT literal write) + `idx.put(taskUuid, unit)` (DIRECT persist). That both (a) drops QA-Review→In-Progress and (b) BYPASSES the seam + `deriveStatusEnum` (the sole 4-state writer, MvcBoundaryGuard) — an out-of-seam direct-status-write, the very anti-pattern R37.11 closed.
- **`deriveStatusEnum` (task-status.ts:16-21):** status = the HIGHEST-order CHECKED **top-level** box (Planned<In Progress<QA Review<Done); **indented sub-steps are IGNORED**. ⇒ a `Processing Change Requests` sub-step under a still-`[x]` QA Review does NOT drop the state — QA Review is preserved BY CONSTRUCTION.
- **Done gate (task-policy.ts:82-84):** Done needs `testing` (a two-keyed passing Test) AND `approvedBy` (Tron verdict). Both.
- **CR mint (server.ts:1626):** `ior:class:ChangeRequest`, `ownerIor → the TASK`, `task`, `requirements`, `status:'Open'`, pushed to `task.changeRequests[]`. ⇒ it hangs off the TASK (navigation), NOT the Test (chain) → renders "no chain path". Test `c4f8a1d6` is itself ORPHANED (no chain path).

## (1) TEMPLATE + DERIVATION — QA-Review kept, In-Progress never, Done blocked by an open CR
- **ONE canonical template:** add `  - [ ] Processing Change Requests` as an INDENTED sub-step under `- [x] QA Review` in the single task template (task-status.ts / the template source) — NOT per-view (a per-view edit drifts; single-source, L2). Sub-steps are ignored by deriveStatusEnum, so the top-level state is untouched.
- **Delete the regression:** remove `m.status = 'In Progress'` + the direct `idx.put` from `declineToChangeRequest`. Decline instead routes through **`UnitController.apply`** (the seam) with a checklist intent that KEEPS `QA Review [x]` and ensures `Processing Change Requests` is OPEN `[ ]` (the open-CR marker). `deriveStatusEnum` then yields **QA Review** (top-level unchanged) — never In Progress — and status stays DERIVED (fixes the seam-bypass + MvcBoundaryGuard violation). Emit fires (live).
- **Done blocked BY CONSTRUCTION (terminal-set tie-in):** extend the Done evidence gate (task-policy.ts) — Done requires `testing` + `approvedBy` + **zero OPEN changeRequests** (the `Processing Change Requests` sub-step resolved). An open CR → `REFUSED …→Done` (fail-loud). So a task with an open CR **cannot** be Done, structurally; the QA-Review achievement is kept while the CR is processed.

## (2) CR CHAIN SEMANTICS — the CR is a CHILD OF THE CURRENT TEST
- **Re-parent the CR to the Test** (the evidence the decline contests), not the task: mint with `ownerIor → ior:instance:<testUuid>` + link into the Test's children (`Test.changeRequests[]` forward mirror, bidirectional with `CR.ownerIor → Test`). The Test = the task's chain's current two-keyed passing Test (task → coveredRequirements → chain → `Impl.tests[]` → Test; here `c4f8a1d6`).
- **Chain render:** `Req → UseCase → Class → Method → Impl → Test → [ChangeRequest]` — the CR (a `ChangeRequest`, RequirementTemplate-rendered) hangs off the Test as a **re-examination branch**, no longer "no chain path". The task keeps `task.changeRequests[]` as the NAV mirror (for the sub-step count), but the CHAIN home is the Test.
- **Pre-existing gap to fix first:** Test `c4f8a1d6` is ORPHANED (no `Impl.tests[]` back-link) — wire it into its Impl so the Test HAS a chain path, THEN the CR hangs off it. (Chain-integrity; the CR can't render on-chain under a Test that is itself off-chain.)

## (3) RE-EVALUATION SEMANTICS — an open CR STALES the Test's pass + the Requirement's acceptance (fail-visible)
The interesting part: a new fact (the CR) must make the downstream GREEN re-examined, not silently still-green.
- **The Test's pass becomes `pass-pending-CR` (contested):** an open CR on a Test → its two-keyed pass does NOT count as satisfied `testing` evidence. The evidence gate's `testing` check gains a predicate: *a Test with an open CR against it is contested → not satisfied*. So the pass is DERIVED-stale from the open CR (single-source: the CR's existence, not a second flag to sync).
- **The Requirement's acceptance is RE-EXAMINED (`satisfied-pending-CR`):** an open CR on the chain marks the requirement's acceptance pending — NOT silently satisfied/Done, and NOT a full reopen (Tron keeps the QA-Review achievement). Its Done/satisfied is blocked + VISIBLY pending.
- **THE GATE (fail-VISIBLE, never silent):** "a task with an OPEN CR cannot be Done AND its Test cannot count as satisfied evidence." Assertions:
  1. Done-gate: any open `changeRequests` on the task → Done REFUSED (part 1).
  2. Evidence-staleness: a Test with an open CR on its chain → its pass does NOT satisfy `testing` (contested) — so even QA-Review→Done evidence is stale while the CR is open.
  3. Visibility at every level (carry the cause, R-C6 / L15 no-silent): the `Processing Change Requests` sub-step (task), the CR node under the Test (chain), a `pass-pending-CR` marker on the Test, `satisfied-pending-CR` on the Requirement. A green that survives the CR = RED.
  - **stub-must-fail:** open a CR on a passing Test → the Test shows `pending-CR` + Done REFUSED; resolve/close the CR → the pass counts again + Done reachable + the sub-step ticks. (A pass that stays green with an open CR, or a Done that succeeds with an open CR, = the gate failing.)
- **CR lifecycle:** `Open → Resolved/Closed`. On resolve (the change made + re-verified, or withdrawn), the sub-step ticks, the Test un-contests, Done becomes reachable — all DERIVED from the CR status, single-source.

## Unifying principle + handoff
Everything derives from ONE fact (the CR's existence/status): status stays QA-Review (sub-step ignored by deriveStatusEnum), Done blocks (open-CR gate), the Test pass contests (derived-stale), the requirement re-examines. No second source to drift (L2), nothing silent (L15), the new fact propagates visibly by construction (the day's family). req mints the requirement + ACs; expert implements: template sub-step, decline-through-seam (drop the In-Progress literal), Done-gate zero-open-CR, CR-parent-to-Test + wire the orphaned Test, evidence-staleness predicate, the fail-visible markers. Gate = the 3 assertions + stub-must-fail, report-only→strict. Reuse deriveStatusEnum / EVIDENCE_GATE / UnitController.apply / the R40.18 sub-step primitive — no new machinery.
