## THE MODE FORK — RULED: presentation != function (keep the preview surface, host the primitive in it)
The room uses `setMode('preview')`/previewPanel + RbPanZoom media pan-zoom + chat-drawer coexistence; renderDetailForRef uses `setMode('detail')`/detailPanel. **RULING: (A) KEEP the room's preview surface, host the RbDetailBase element INSIDE it — mode is a POSITION, not a second FUNCTION.** This is the presentation!=function invariant (R31.4 DRY-drawer / CONCEPT-scrollable-viewport, drawer=Details-compartment position-only). Rationale: the preview surface + pan-zoom + chat-coexistence are legitimate PRESENTATION for a room media-tap; switching room taps to detail-mode (option B) would lose them or force re-implementation = drift. So:
- The FUNCTION (ONE model-source + renderDetail + fail-LOUD) comes from the primitive regardless of which panel hosts it.
- **Media pan-zoom becomes a `renderDetail` concern:** RbFileDetail.renderDetail(ctx) media-auto-renders an image with RbPanZoom (composes with the Phase-A sub-question below). Then the room's previewPanel simply HOSTS that element; the drawer's `setMode` stays a CSS/layout branch on ONE element, never a render fork.
- Net: one element renders file-detail + media + pan-zoom + fail-loud, hosted in detailPanel (trace-page) OR previewPanel (room) by mode. Convergence achieved without losing the room's affordances.

## PHASE-A SUB — RATIFIED with a boundary: renderDetail may supplemental-fetch
YES — `renderDetail(ctx)` may do its OWN supplemental fetch (`fetchDetailData` for children/source-links) + media auto-render, while the base owns model + fail-loud (the 8 existing subclasses already do this = the established pattern). **BOUNDARY (the invariant that keeps it ONE funnel):** the base owns (a) the ONE primary model-source resolution and (b) the fail-LOUD `renderUnresolved` on an unresolved ref. The subclass's supplemental fetch is for SECONDARY data AFTER the model resolves — a supplemental-fetch failure DEGRADES THAT SECTION (a visible "couldn't load children" inline), never a silent whole-element fail and never a SECOND not-found/thin path. No subclass re-implements the primary resolution or a second funnel.

## Hazard-gate honesty — the gate is BLIND BY INHERITANCE (PO mechanism, a text-not-structure sibling)
The hazard-gate asserts "0 own-funnel outside the primitive," yet these 2 violators EXIST while the gate is GREEN. **PO named the exact mechanism: the gate is BASE-CLASS-ENFORCED — it scans RbDetailBase SUBCLASSES for own-funnels; a component that `extends HTMLElement` (does NOT inherit RbDetailBase) is INVISIBLE to it. "The guard cannot see what does not inherit from it."** So RbFileDetail/RbWebItemDetail evade it entirely — the gate is green because it never looked at them.
- **This is a STRUCTURAL SIBLING of the name-keyed lint (text-not-structure family):** the gate keyed its SCOPE to the ACTORS' membership (inheritance) instead of the HAZARD's presence — evadable by not-inheriting, exactly as the name-keyed lint was evadable by renaming. Same root: [[scan-the-hazard-not-the-actors]]. New evasion vector (inheritance-scope), same cure.
- **FIX (scan the hazard, not the inheritance set):** the hazard-gate must scan for the HAZARD SHAPE — a **detail-ish component** (renders a detail view / has its own `/api/ior` fetch + own `connected/attributeChanged` funnel + own not-found path) that does **NOT route through the primitive** — regardless of base class. "detail-ish AND own-funnel AND not-RbDetailBase" → RED. Then a future straggler that `extends HTMLElement` cannot hide by not inheriting. (Self-bite: plant an `extends HTMLElement` detail element with an own funnel → must flag.)

Do NOT leave it a silent hole (r4011/coverage-self-report lesson). This is a concrete specimen for the lint-over-lints / text-not-structure family: **a guard keyed to inheritance is a guard keyed to the actors.**
