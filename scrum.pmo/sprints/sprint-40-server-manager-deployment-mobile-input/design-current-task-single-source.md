## MEASURED ground truth (first-hand, not relayed)
- **Definition A — the DESIGNATION resolver** (correct): `CurrentSprint.getThreeSlots` (CurrentSprint.ts:270) honors the owner's `currentTaskUuid` **EXPLICIT-WINS-WHILE-VALID** — a make-current designation (server.ts:1868, R40.49) written through the seam wins iff the task is in the resolved sprint AND status ∈ {Planned, In-Progress, QA-Review}, expiring at Done/re-designate/gone (observed via StaleSteerLog). The scoreboard/pin read this.
- **Definition B — a parallel HEURISTIC** (rogue): `derivedCurrentTaskUuid` (server.ts:1388) **ignores the designation entirely** — loops all Tasks, keeps only `deriveStatusEnum==='In Progress'`, picks max `lastAdvancedAt`. `attachTaskPinRole` (:1400) tags `pinRole='current'` off THIS. The action-bar's Set-Current visibility (action-applicability.ts:34, hidden when `taskRole==='current'`) rides B.
- ⇒ T37.25 renders "current" because it's the newest In-Progress task — regardless of what Tron designated. And a QA-Review task (T37.24) can NEVER be current under B (In-Progress-only filter), so its Set-Current button always shows.

## (a) RULING — ONE source of truth for "current task"
**`pinRole` MUST resolve from the SAME designation-honoring resolver as the pin/scoreboard, never a parallel derivation. DELETE `derivedCurrentTaskUuid` — it is the second source.**
- The server already computes the pin slots per request via `CurrentSprint.slotsFrom(idx, resolveSprintPin(idx, hint), singleton.currentTaskUuid)`. **Compute those slots ONCE per request; `attachTaskPinRole` reads `slots.current?.uuid`** and sets `pinRole = (slots.current?.uuid === taskUuid) ? 'current' : 'other'`. No second computation, no second inputs.
- ★ INVARIANT: current-task selection has exactly ONE definition site (`getThreeSlots`); every consumer READS its output. `pinRole`, the action-bar, the scoreboard, and the tree highlight all derive from the SAME `slots.current` — so "what Tron set" and "what renders current" are the same value by construction. (Beware the subtler divergence: even calling `slotsFrom` with DIFFERENT inputs (a different resolvedSprint / a stale currentTaskUuid) is a second source — hence compute-once-pass-down, not re-call.)

## (b) RULING — designation EXPIRY behavior
Routing `pinRole` through `getThreeSlots` inherits the correct expiry FOR FREE: EXPLICIT-WINS-WHILE-VALID already expires the designation at Done/re-designate/gone and falls back to the derived current. **The rule: `pinRole` has NO opinion of its own — it MIRRORS `slots.current`, including on expiry.** Whether the *fallback* should be a fresh derivation vs **honest absence** is a `getThreeSlots`-level policy decided in ONE place:
- RECOMMEND: on expiry with no valid designation AND no unambiguous chain-current, **honest absence** (no task tagged `current`; the Set-Current button shows on all) is more truthful than silently promoting a guess to "current" — the guess is exactly what made this defect invisible (a wrong "current" that looked authoritative). A derivation-fallback is acceptable ONLY when it is unambiguous (a single active task); ties/ambiguity → absence, never a silent pick (fail-closed, the R3 instinct). Decide it in `getThreeSlots`; `pinRole` follows.

## (c) WHY check:pin-single-source MISSED a second definition
It scans the **ACTORS, not the HAZARD.** `check-pin-single-source.ts:15-18` is a **2-regex blocklist** of known-rogue SHAPES: `filter(status==='Active')` and `sprintName→number.find`. Both are SPRINT-level derivations. `derivedCurrentTaskUuid` is a TASK-level derivation of a different shape (`deriveStatusEnum==='In Progress'` + max `lastAdvancedAt`) — not in the blocklist → **passes green while a second source ships.** Same failure class as the uses-builder-vs-typed-result gate and the marker-name-vs-scope gate: **a blocklist of code shapes can never prove a single-source invariant, because the next divergence is always a new shape.** [[scan-the-hazard-not-the-actors]]

**What it MUST assert instead (by-construction, unevadable):** the HAZARD is "a function returns a task uuid selected as *the current one*." Assert **that selection has a single definition site**:
- ONE sanctioned accessor produces the current-task (e.g. `currentTaskUuid(idx)` wrapping `slotsFrom(...).current`); it is the only place the selection is computed.
- The gate proves single-source not by pattern-blocklisting but by the selection being **structurally nameable**: no other function body loops `ior:class:Task` units and returns one uuid chosen by a status/timestamp comparison. The hazard names itself (a Task-selection loop returning a uuid), so "0 such selections outside the sanctioned accessor" proves single-source in one number — the same shape as "0 raw insertAdjacentHTML outside the primitive."
- **Its OWN stub-must-fail:** seed a second function that returns a task uuid by a status+timestamp scan (i.e. re-introduce exactly `derivedCurrentTaskUuid`) → the gate MUST go RED. **Today the gate is GREEN with `derivedCurrentTaskUuid` present** = proof it asserts the wrong property; the fixed gate must RED on this exact case as its RED baseline. (R2 stub-must-fail: a gate that was never RED on the real defect proves nothing.)

## (d) RULING — the In-Progress-only filter IS a bug (same retired invented-status-policy)
Tron: "reviewing IS working." The designation-validity set already correctly = {Planned, In-Progress, QA-Review} (CurrentSprint.ts:266). But `derivedCurrentTaskUuid`'s In-Progress-**only** filter (:1393) re-invents the status-policy we retired at T37.26 — it excludes QA-Review from ever being current, which is why T37.24 (QA-Review) always shows Set-Current. **Current-eligibility must be {Planned, In-Progress, QA-Review} everywhere.** Deleting `derivedCurrentTaskUuid` (a) removes the offending filter; the ruling ties (a)+(d): ensure `getThreeSlots`' fallback derivation uses the SAME {P/IP/QA} eligibility, not In-Progress-only — one eligibility definition, one current definition.
