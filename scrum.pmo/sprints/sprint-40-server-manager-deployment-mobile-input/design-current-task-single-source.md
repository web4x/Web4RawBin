## (a) RULING — ONE source of truth for "current task"
**`pinRole` MUST resolve from the SAME designation-honoring resolver as the pin/scoreboard, never a parallel derivation. DELETE `derivedCurrentTaskUuid` — it is the second source.**
- The server already computes the pin slots per request via `CurrentSprint.slotsFrom(idx, resolveSprintPin(idx, hint), singleton.currentTaskUuid)`. **Compute those slots ONCE per request; `attachTaskPinRole` reads `slots.current?.uuid`** and sets `pinRole = (slots.current?.uuid === taskUuid) ? 'current' : 'other'`. No second computation, no second inputs.
- ★ INVARIANT: current-task selection has exactly ONE definition site (`getThreeSlots`); every consumer READS its output. `pinRole`, the action-bar, the scoreboard, and the tree highlight all derive from the SAME `slots.current` — so "what Tron set" and "what renders current" are the same value by construction. (Beware the subtler divergence: even calling `slotsFrom` with DIFFERENT inputs (a different resolvedSprint / a stale currentTaskUuid) is a second source — hence compute-once-pass-down, not re-call.)

## (b) RULING — designation EXPIRY behavior
Routing `pinRole` through `getThreeSlots` inherits the correct expiry FOR FREE: EXPLICIT-WINS-WHILE-VALID already expires the designation at Done/re-designate/gone and falls back to the derived current. **The rule: `pinRole` has NO opinion of its own — it MIRRORS `slots.current`, including on expiry.** Whether the *fallback* should be a fresh derivation vs **honest absence** is a `getThreeSlots`-level policy decided in ONE place:
- RECOMMEND: on expiry with no valid designation AND no unambiguous chain-current, **honest absence** (no task tagged `current`; the Set-Current button shows on all) is more truthful than silently promoting a guess to "current" — the guess is exactly what made this defect invisible (a wrong "current" that looked authoritative). A derivation-fallback is acceptable ONLY when it is unambiguous (a single active task); ties/ambiguity → absence, never a silent pick (fail-closed, the R3 instinct). Decide it in `getThreeSlots`; `pinRole` follows.

**What it MUST assert instead (by-construction, unevadable):** the HAZARD is "a function returns a task uuid selected as *the current one*." Assert **that selection has a single definition site**:

## ★ RATIFICATION REFINED — reduce-to-ONE, not return-TYPE (PO evasion catch, 2026-08-21; supersedes the array-return phrasing above)
My prior ratification said "exclude array-typed returns." PO caught the EVASION that opens: a real second source hides by returning its single winner WRAPPED — `return [best]` (array-of-one) or `return { uuid: best }` (object). Excluding by return-TYPE would then let a disguised reduce-to-one evade. **Unevadability is the property, not scalar-ness.** So the discriminator is the BODY, not the return type:
- **reduce-to-ONE (HAZARD, must RED):** a single-winner accumulator (`best`/`current`) conditionally overwritten in the loop to keep ONE, then returned — bare OR wrapped (`[best]`, `{uuid:best}`, `.at(0)`). derivedCurrentTaskUuid = this.
- **collect-ALL (NOT the hazard):** `.push(...)` accumulates EVERY match into an array, returns the array. assertStatusConsistent = this.
The signal is **single-winner reduction (keep-if-better, no push-all) that yields a task uuid**, unevadable by wrapping. Return-type array-ness is a weak proxy that is both over-broad AND evadable; the reduction-shape is the design's actual hazard.

**PO discriminator answered (would this have been written from the DESIGN TEXT ALONE, pre-finding?):** YES. Design §(c) line 24 verbatim: "no other function body loops `ior:class:Task` units and returns ONE uuid chosen by a status/timestamp comparison." "Returns ONE chosen" ⇒ reduce-to-one ⇒ a return-ALL-offenders function is excluded BY THE DESIGN TEXT, before anyone saw finding-2. Principled, not answer-fitting. (The IMPRECISE part was the expert's implementation of "returns one" as "scalar return type"; the precise implementation is "reduces to a single winner." Refining an imprecise signature to match an already-stated hazard = principled; the evasion catch proves scalar-type was the imprecise proxy.)

**assertStatusConsistent = genuinely a DIFFERENT hazard (reasoned out-of-scope, not convenient):** it is status-offender DETECTION — finds EVERY Task whose declared status ≠ derived status (`StatusOffender[]`, FALSE-DONE/MALFORMED/DRIFT), a consistency auditor for reporting. It never selects "the current task"; it returns ALL drift, not ONE chosen. Different hazard entirely (drift-detection vs current-selection) → legitimately out of scope.

**HARD CONDITIONS before the clean baseline commits (PO):** the selftest MUST include, as stub-must-fail negatives proving unevadability — (i) `return [best]` (reduce-to-one wrapped in array-of-one) → MUST RED; (ii) `return { uuid: best }` (wrapped in object) → MUST RED; (iii) `return offenders` (collect-all `.push`) → must NOT flag. The expert's 5/5 missed the array-return case; these three close it. Then re-run → gate reds ONLY on derivedCurrentTaskUuid → commit the clean RED baseline → `redBaselineEvidence` on R40.56.
