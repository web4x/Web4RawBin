## (a) RULING — ONE source of truth for "current task"
**`pinRole` MUST resolve from the SAME designation-honoring resolver as the pin/scoreboard, never a parallel derivation. DELETE `derivedCurrentTaskUuid` — it is the second source.**
- The server already computes the pin slots per request via `CurrentSprint.slotsFrom(idx, resolveSprintPin(idx, hint), singleton.currentTaskUuid)`. **Compute those slots ONCE per request; `attachTaskPinRole` reads `slots.current?.uuid`** and sets `pinRole = (slots.current?.uuid === taskUuid) ? 'current' : 'other'`. No second computation, no second inputs.
- ★ INVARIANT: current-task selection has exactly ONE definition site (`getThreeSlots`); every consumer READS its output. `pinRole`, the action-bar, the scoreboard, and the tree highlight all derive from the SAME `slots.current` — so "what Tron set" and "what renders current" are the same value by construction. (Beware the subtler divergence: even calling `slotsFrom` with DIFFERENT inputs (a different resolvedSprint / a stale currentTaskUuid) is a second source — hence compute-once-pass-down, not re-call.)

## (b) RULING — designation EXPIRY behavior
Routing `pinRole` through `getThreeSlots` inherits the correct expiry FOR FREE: EXPLICIT-WINS-WHILE-VALID already expires the designation at Done/re-designate/gone and falls back to the derived current. **The rule: `pinRole` has NO opinion of its own — it MIRRORS `slots.current`, including on expiry.** Whether the *fallback* should be a fresh derivation vs **honest absence** is a `getThreeSlots`-level policy decided in ONE place:
- RECOMMEND: on expiry with no valid designation AND no unambiguous chain-current, **honest absence** (no task tagged `current`; the Set-Current button shows on all) is more truthful than silently promoting a guess to "current" — the guess is exactly what made this defect invisible (a wrong "current" that looked authoritative). A derivation-fallback is acceptable ONLY when it is unambiguous (a single active task); ties/ambiguity → absence, never a silent pick (fail-closed, the R3 instinct). Decide it in `getThreeSlots`; `pinRole` follows.

## (c) WHY check:pin-single-source MISSED a second definition

**What it MUST assert instead (by-construction, unevadable):** the HAZARD is "a function returns a task uuid selected as *the current one*." Assert **that selection has a single definition site**:

The hazard names itself (a Task-selection loop returning a uuid), so "0 such selections outside the sanctioned accessor" proves single-source in one number — the same shape as "0 raw insertAdjacentHTML outside the primitive."
- **Its OWN stub-must-fail:** seed a second function that returns a task uuid by a status+timestamp scan (i.e. re-introduce exactly `derivedCurrentTaskUuid`) → the gate MUST go RED. **Today the gate is GREEN with `derivedCurrentTaskUuid` present** = proof it asserts the wrong property; the fixed gate must RED on this exact case as its RED baseline.
