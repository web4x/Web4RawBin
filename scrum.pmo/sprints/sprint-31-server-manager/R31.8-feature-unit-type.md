**Tron (2026-07-21):** *"model a scenario-first unit type Feature. it is referenced by all implementations. so ServerManager is a feature and itself references all implementations belonging to it… so both-way consistent navigation. additionally it references the user's scenarios that are allowed to use it from the user profile. a second feature on the same rights as the server manager is the FeatureManager, that allows to enable and disable features on user profiles. add a list of features to my profile this way where the server manager is currently."*

## The `Feature` typed unit (`ior:class:Feature`)
A first-class typed scenario unit — the PRODUCT layer, linking code (implementations) to users (grants):
- `name`, `description`, `icon`
- **`implementations: ref[]`** → every Impl unit belonging to this feature. **BOTH-WAY:** each Impl carries a back-ref `feature` → its Feature, so navigation is consistent in both directions (Feature → its impls; impl → its Feature). Mirror-maintained like Class.methods[]/Method.ownerIor.
- **`allowedUsers: ref[]`** → the **user profile scenarios** allowed to use this feature. Both-way with the profile: `profile.features` ↔ `Feature.allowedUsers`.

## Access control — data-driven (generalizes R31.2), architect owns the security design
- A feature's access check becomes: **is the viewing user in `Feature.allowedUsers`?** — data-driven, replacing the hardcoded `OWNER_TOKEN` literal for feature-gating. This aligns with typed-scenario-configs (R31.7): grants are DATA, not hardcoded.
- ★ **Bootstrap / root-of-trust (flag to architect):** FeatureManager edits grants, so it is the critical gate — it must be the strongest-gated feature, seeded to the owner (Tron) at bootstrap so he can grant/revoke everything else.
