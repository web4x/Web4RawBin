## ⚠ 3 REFINEMENTS (feature-UI, scenario-first)
1. **Children = ITEMVIEWS TO THE USER SCENARIO, not additional uuids.** The granted-user child nodes must be itemviews of the **actual user scenario unit** (the person's profile) — navigate to / render the REAL user, not standalone opaque-uuid entries. In the shot the children are generic uuid rows (subtitle just repeats the name); they should be proper itemviews bound to the user scenario.
   - ★ SECURITY (architect owns): the URL-addressable ref STAYS opaque per FIX-2 (`<featureUuid>:<sha256[:16]>`, no raw token). The itemview resolves + navigates to the user server-side (owner-gated) — display/nav resolves the user, the ref stays hashed. Do NOT re-expose the token to satisfy "itemview to user scenario."
2. **Details = the user's PROFILE.** The drawer detail should render the user's **full profile scenario** (RbProfileDetail, masked/owner-gated — like the profile-in-drawer flow already designed), NOT just `name + d5e3bb07…` opaque id + a button.
3. **Drawer layout: actions under the bar, content below.** Render the **actions (Revoke)** directly under the drawer grab-bar, then **all further content (the profile details) below** the actions. Order: `[grab-bar] → [actions: Revoke] → [content: profile]`. (Revoke button itself is good, just reposition to the top of the drawer body under the bar.)
