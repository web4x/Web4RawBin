# R31.8b DESIGN — FeatureManager OPEN + admin VIEW (robbin-architect 2026-07-22, Tron: "renders but doesn't OPEN")
Tron/PO: FeatureManager renders in the profile but clicking it does nothing. Design (1) the OPEN — consistent with how ServerManager opens, via the SHARED default drawer (positioning≠function, reuse R31.4/R31.5, NO new overlay fork); (2) the admin VIEW — list Features → per-feature allowedUsers → grant/revoke, driven by the proven owner-gated POST /api/feature-manager.

## MEASURED — how ServerManager opens today (the consistency reference)
`renderFeatureGrants` (server.ts:915-939) lists each `m.features` entry as an `<a>`. **Server Manager** (:933): onclick → `POST /api/server-manager/session` (mint the httpOnly sm_session cookie via the live owner token) → on ok `location.href='/server-manager'` (page nav). The `/server-manager` PAGE is gated by `requireFeatureAccess('Server Manager')` (:953, data-driven membership) and hosts the shared `rb-detail-drawer` — the tree + the terminal (R31.4) render as drawer detail-views (positioning≠function). **Every OTHER feature (incl FeatureManager, :934): `onclick=preventDefault()` = does NOTHING** ← the bug.

## (1) FeatureManager OPEN — the SAME mechanism, shared drawer (no overlay fork)
Wire the FeatureManager entry EXACTLY like ServerManager (consistency): onclick → `POST /api/server-manager/session` (or a generalized `/api/feature-session`) to mint the httpOnly cookie via the live owner token → `location.href='/feature-manager'`.
- **`/feature-manager` PAGE** (new, mirrors `/server-manager`): gated by `requireFeatureAccess('Feature Manager')` (DATA-DRIVEN view access — owner is a member via bootstrap; a granted non-owner could view, but WRITES stay owner-only, below). Page shell hosts the SHARED `rb-detail-drawer` and auto-opens the admin view as a DETAIL-VIEW via the standard selection→`renderDetailForRef` flow — `rb-feature-manager-detail` (a new detail element like `rb-terminal-detail`), tagMap `feature:<uuid>`→`rb-feature-manager-detail`. positioning≠function: inline (landscape) / bottom (portrait) via the R31.5.7 `data-position` when it lands; NO bespoke overlay, NO new drawer component.
- Generalize renderFeatureGrants:934 — the `else` branch (currently preventDefault) becomes: mint-cookie + nav to the feature's page (feature model carries its `route`/page, or FeatureManager is the 2nd known route). Keep it data-driven off `m.features` (each feature entry knows how to open).
- **Consistency note:** both features open via cookie-mint + page-nav + the SHARED drawer hosting a detail-view. The R31.4 terminal + this FeatureManager admin view are BOTH `rb-detail-drawer` detail-views = the DRY drawer family (no fork). (A later unification could open features in a drawer ON /profile without a page-nav; for now page-nav matches ServerManager.)

## (2) FeatureManager ADMIN VIEW — `rb-feature-manager-detail`
A detail-view (drawer content) that lets the OWNER manage grants:
- **Read:** NEW `GET /api/feature-manager` (gated `requireFeatureAccess('Feature Manager')`) → returns `[{ uuid, name, icon, allowedUsers:[token…] }]` for ALL Features (scan `ior:class:Feature`). The view lists Features → per-feature its granted users (allowedUsers).
- **Grant control:** per feature, "add user" input → resolve the target to a TOKEN (paste token, or a short LINK-CODE that maps to a token — link-code = a convenience layer, grant-by-token is the stable identity) → `POST /api/feature-manager {action:'grant', feature:<uuid>, token}` (owner-gated). On 200, re-fetch + re-render (the granted user appears; their access flips live — proven at slice-b).
- **Revoke control:** per granted user, a revoke button → `POST /api/feature-manager {action:'revoke', feature:<uuid>, token}` (owner-gated). On 200, re-fetch (the user disappears; their access 403s immediately — revoke-immediate, proven).
- Uses the PROVEN owner-gated `POST /api/feature-manager` (server.ts:979, requireOwnerHttp, INV-F4 root-of-trust). Grant takes the Feature **uuid** (expert is making grant/revoke accept name-OR-uuid; the view has the uuid regardless).

## SECURITY (preserve R31.8 invariants — no weakening)
- **VIEW access = DATA-DRIVEN** `requireFeatureAccess('Feature Manager')` (membership; owner via bootstrap). Consistent with ServerManager. A future granted non-owner could VIEW but their grant/revoke POSTs still 403 (writes are owner-only) — security-correct (see-but-not-act), and today only the owner is a member.
- **WRITES (grant/revoke) = HARDCODED-owner** `requireOwnerHttp`/assertOwner (INV-F4 root-of-trust) — UNCHANGED, the distinct `/api/feature-manager` POST path, no self-grant. INV-G2 OWNER_TOKEN literal ==1. NO new overlay/page bypasses the gate (the `/feature-manager` page + `/api/feature-manager` GET/POST all gated).
- Reuse the shared `rb-detail-drawer` (R31.4/R31.5) → positioning≠function, one drawer family, no fork = the recurring-regression class stays closed.
