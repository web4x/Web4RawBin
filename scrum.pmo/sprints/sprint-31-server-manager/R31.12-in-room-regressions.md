## R31.12 #2 ROOT CORRECTED (tester @390 real-tap gate, robbin-architect 2026-07-27) — ★ I OWN the miss: it IS a real regression (banner overlay), not a missing affordance
My earlier code-analysis (title-no-handler / ✏️→openRoomEditor modal) was right IN ISOLATION but MISSED the OVERLAY — which only manifests at a real device safe-area (Tron's notched iPhone). The tester's `elementFromPoint` @390 caught it: at BOTH the title AND the ✏️, the topmost element == `rb-update-banner` → taps INTERCEPTED → settings don't open via EITHER. The always-worked ✏️ is now BLOCKED = why Tron said "doesn't open ANYMORE". [[device-qa-regression-means-missing-ac]] — the second time this session a tester device/@390 gate caught what static analysis couldn't (R31.11 stamp was the first).

### ROOT (measured + cited)
- `rb-update-banner.ts:71`: `:host { display:block; position:fixed; top:0; left:0; right:0; z-index:2000; }` — a FULL-WIDTH fixed overlay at the very top, ABOVE the app/room header, default `pointer-events:auto`. `.banner` (:72) `padding-top: calc(10px + env(safe-area-inset-top))` → ~47px tall on a notched device.
- `app.ts:100-101`: `<rb-update-banner>` is `document.body.prepend`ed on EVERY load — always present.
- **★ ACUTE TRIGGER = the client-only version skew:** `rb-update-banner.ts:51` fires `showBanner(config.version)` whenever `config.version !== __BUILD_VERSION__`. The R31.12 client-only ship made client `__BUILD_VERSION__=0.7.140` while server `/api/config=0.7.139` (boot-stamped, not restarted) → **`0.7.139 !== 0.7.140` → the banner shows on every load right now**, overlaying the header. (It even offers a DOWNGRADE — config is OLDER than build — a second smell.) Every client-only ship reproduces this skew.
- **BISECT:** the fixed top:0 z2000 overlay banner = **R30.14** (f04f4be98 v0.7.22 "BANNER-FIRST" / e53764137 v0.7.49). It silently blocks header taps WHENEVER it's shown over a header; frequent client-only ships (version skew) keep it up → now chronic.

### FIX (hand expert) — correct-by-construction, two layers
| # | File:line | Fix |
|---|-----------|-----|
| 1 (structural, PRIMARY) | `rb-update-banner.ts:71` `:host` | `:host { pointer-events: none; }` ALWAYS (the element itself NEVER intercepts taps) + `.banner { pointer-events: auto; }` (:72, the actual strip + Update-Now button stay tappable WHEN shown). Header taps pass THROUGH the host by construction, banner still works when present. |
| 2 (footprint) | `rb-update-banner.ts:71` `:host` | default `:host { display: none; }`; `showBanner()` adds a `[shown]` attr → `:host([shown]) { display:block; position:fixed; top:0; …; }`. No update → zero footprint (no visual overlap either). |
| 3 (skew trigger) | `rb-update-banner.ts:51` | showBanner ONLY when `config.version` is a GENUINE NEWER version than `__BUILD_VERSION__` (semver-greater), not merely `!==` → a client that's AHEAD (client-only ship) does NOT raise a spurious downgrade banner. Kills the acute chronic-overlay trigger. |

- Row 1 alone closes the tap-interception (Tron's regression); rows 2+3 remove the visual overlap + the spurious-banner source. Recommend ALL THREE.
- **CLIENT-only** (no restart). GATE (tester @390 real device / notched safe-area): `elementFromPoint` at the room title AND ✏️ == the header/button (NOT rb-update-banner) → title-tap AND ✏️ open settings; a genuine newer-version banner still shows + Update-Now still taps; no spurious banner on version skew. #1 chat gate unchanged.
