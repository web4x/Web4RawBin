# R31.7 — DRY single-source version + typed config scenarios (Tron principle)

**Tron (2026-07-21):** *"we should always do DRY so ONE single source for the version as much as possible… no scattered fragile locations. scenarios are the ONLY configs we want. TYPED SCENARIOS."*

## Root the incident exposed
The phantom "update available for 7.99" happened because the **version is scattered** across ≥4 hand-maintained locations that desynced:
- `package.json` "version" (uncommitted-edited to 0.7.99)
- `src/public/sw.js` `CACHE_NAME` (0.7.102)
- `src/public/dist/build-manifest.json`
- `/api/config` (reads package.json per-request)
Any one drifting → phantom downgrade + broken PWA update. Scattered = fragile by construction.

## Principle (make it correct-by-construction) — Tron: "TYPED SCENARIO UNITS"
1. **VERSION = ONE TYPED SCENARIO UNIT source of truth.** The version lives in a single typed scenario unit (`ior:class:…` with a typed/schema'd `version` field) — the SAME unit mechanism as every other scenario, just typed. Every consumer — package.json version, `sw.js` CACHE_NAME, build-manifest, `/api/config`, any UI version badge — is **GENERATED/DERIVED** from that one unit, never hand-copied. They *cannot* desync because there is one source unit.
2. **CONFIGS = TYPED SCENARIO UNITS.** No scattered fragile config (hardcoded constants, `.env` sprawl, ad-hoc JSON, hand-maintained copies). Every config is a **typed scenario unit** (schema-validated) — the ONE config mechanism, consistent with data-on-disk-is-truth. Start with version; extend to other configs as far as practical ("as much as possible").
3. This also removes the landmine class the incident exposed: no hand-maintained duplicate can be stray-checked-out to an old value, because the duplicates don't exist — they're generated from the one unit.

## ACs (req to formalize scenario-first)
- A single **typed version scenario** (e.g. `ior:class:Config`/`Version` with a typed `version` field) = THE source.
- **Build/deploy GENERATES** package.json version + `sw.js` CACHE_NAME + build-manifest from it (no hand-edit; a generator step, like requirements.md is a generated view).
- `/api/config` + any version display **READ** the one source.
- **INVARIANT (guard/CI):** `served == committed == SW == scenario` by construction; a check fails loudly on any divergence (this is the served==committed==HEAD phantom-guard, now rooted in one source).
- Typed-config pattern other configs derive from (version first).

## Recurrence fixes — FOLD INTO R31.7 (do NOT fragment into a separate guard)
The incident root-cause (expert): a MANUAL `git checkout <old-commit> -- server.ts package.json build-manifest` to inspect the old version, left unrestored (no reflog). R31.7 absorbs all three recurrence fixes as part of the one version-integrity requirement:
- **(a) single typed-unit source + generation** (above) — removes the duplicates that CAN drift.
- **(b) start.mjs pre-deploy guard** — refuse/warn if `server.ts`/`package.json` diverge from HEAD before build+spawn (the working-tree==HEAD guard). Catches a stray checkout before it deploys.
- **(c) boot-stamp `/api/config` version** — stamp version at boot from the ONE unit, NOT a per-request package.json read (kills the "/api/config version lied" confound).
- **team discipline:** inspect old versions with `git show <ref>:<file>` (non-mutating), NEVER `git checkout <ref> -- <file>` (mutates the tree = landmine). Bank + relay to trainer.
