## STEP 1 — DIAGNOSIS (measured the shipped v0.7.132)

### Tron's specific claim "JS instance-switch / component swap" = REFUTED
- Each page creates exactly ONE `rb-detail-drawer` and keeps it: `server-manager.ts:22` (`.trace-page||body`), `feature-manager.ts:19` (`body`), `trace-page.ts:35`, `scenario-view.ts:38`. NO code swaps it for `rb-compartment`, re-mounts it, or `matchMedia`-recreates it at any width. **It is the SAME instance across the breakpoint.** No JS instance-switch exists.

### But Tron is RIGHT there's a real discontinuity + a DRY fork — the actual root:
1. **HARD CSS media-query FLIP at 1025px = the JUMP.** `app.css:277 @media(min-width:1025px) .trace-page rb-detail-drawer { position:static!important; flex:1; border-left; max-height:100vh; … }` abruptly repositions the SAME element from bottom-drawer → static side-panel at exactly 1025px. One-pixel width change → discontinuous layout = the jump. (SM drawer is in `.trace-page` so it flips; FM drawer is on `body` so it does NOT flip — an inconsistency, below.)
2. **DRAG-BAR resize BREAKS across the breakpoint** — sharper root (expert-measured, corroborated): the drag writes an INLINE `this.style.height = ${clamped}px` (rb-detail-drawer.ts:384 touch / :396 mouse) that **PERSISTS on the element**. Cross to ≥1025px and the drawer becomes `position:static; flex:1` side-panel (app.css:277) — but the STALE inline `height:Npx` from the prior bottom-drag survives and OVERRIDES `flex:1` → the side-panel is stuck at the stale dragged height = "resize broken / behaviour shifts." Compounded by `app.css:310 rb-detail-drawer .drawer-handle{display:none}` hiding the handle ≥1025px so you can't re-drag to correct it. (Height-drag is also semantically wrong for a flex row-child side-panel.)
3. **The DRY fork Tron sensed is REAL but it's the hard media-query, not a JS swap.** Mobile-drawer and desktop-side-panel are TWO CSS presentations bolted on one element via a hard breakpoint, with NO continuous transition — EVEN THOUGH R31.5.7 already BUILT the continuous mechanism: `RbDetailDrawer.applyPosition('inline'|'bottom')` sets `data-position` (rb-detail-drawer.ts:136, Method d48cc0ce). **It has ZERO callers — completely UNWIRED / dead.** The hard media-query is what's live.
4. **Two more gaps:** FM drawer mounts to `document.body` not `.trace-page` (inconsistent w/ SM); the R31.5 composed layout (`rb-strip`/`rb-compartment`) is NOT on the FM/SM pages at all (only /edit R31.5.5) — so "desktop = Details compartment in the R31.5 layout" does not exist yet on these pages.

**VERDICT:** same instance (Tron's instance-switch is refuted), but a real hard-breakpoint CSS discontinuity + an unwired continuous mechanism = the fix Tron wants is exactly right, and the mechanism to do it (data-position) is already built — it just needs WIRING + the hard media-query RETIRED.

## STEP 2 — DESIGN: wire the (existing) continuous mechanism, retire the hard flip, desktop = compartment
ONE `rb-detail-drawer` instance, presentation driven by `data-position` via a CONTINUOUS container-query driver (reuse the R31.5 `RbStrip.observeContainer` ResizeObserver pattern, rb-strip.ts:81-84), NOT a hard `@media`. positioning != function.

'inline' : 'bottom')` — the same pattern as `RbStrip.observeContainer` (decide at a width threshold). Wires the dead R31.5.7 mechanism. The `data-position` mechanism was R31.5.7's whole purpose — R31.9 = WIRE it + retire the legacy hard breakpoint.
