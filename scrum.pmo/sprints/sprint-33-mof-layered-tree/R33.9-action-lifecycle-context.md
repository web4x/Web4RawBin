# R33.9 — Action lifecycle + context-correctness (Tron device critique, 2026-07-31)

**Tron (IMG_4802 diagram-open, IMG_4803 no-diagram):**
> "on the first screenshot i miss the actions, that are wrongly on the second screenshot. in the context of a diagram the buttons make sense. how do they make sense with no diagram selected… the last diagram? that's fragile. think with the architect in lifecycle: new, add, rename, remove, delete"

## The defect (context-model, not a missing button)
- **IMG_4802 — a diagram IS open** (gmapsLinkFor diagram rendered, an element selected in it). Action bar shows DIAGRAM-level actions (+ Add Diagram / Re-Sync / Compile→SVG) but the per-ELEMENT actions (Add to diagram / Discover related / Remove from diagram) are **MISSING** — even though an element is selected inside the open diagram, which is exactly where "remove from THIS diagram" belongs.
- **IMG_4803 — NO diagram open**, an element (TsToModel class) is selected. Action bar shows **"+ Add to diagram" / "Remove from diagram"** — but *which* diagram? There is no diagram context. It implicitly targets **"the last diagram"** = **FRAGILE** (ambiguous, stateful, silently wrong when the last diagram isn't what the user means).
- Net: the membership actions are shown in the WRONG context (no-diagram) and MISSING in the RIGHT context (diagram-open). The "last diagram" implicit target is the fragility Tron is calling out.

## Tron's directive: model the ACTION LIFECYCLE properly (architect)
Think the full verb set with distinct semantics + correct context each:
- **new** — create a NEW class/element (mint a unit). Unit-scope; no diagram required.
- **add** — add an EXISTING element to a diagram (view membership). Requires an explicit diagram TARGET — never an implicit "last diagram".
- **rename** — rename the unit. Unit-scope.
- **remove** — remove from a diagram = VIEW-ONLY (R33.8, unit stays, re-addable). Requires a diagram context (remove-from-WHICH).
- **delete** — delete the underlying UNIT (destructive, ≠ remove). Unit-scope, guarded.

## Context rules (architect to design; PO intent)
- **remove-from-diagram / add-to-diagram are DIAGRAM-CONTEXT actions** — only valid/shown when a specific diagram is the active target. When a diagram is OPEN + element selected → these appear (add/remove THIS element to/from THIS diagram). When NO diagram is open → they must NOT silently target "the last diagram"; either hide/disable them or require an explicit diagram pick.
- **new / rename / delete are UNIT-scope** — valid on a selected element regardless of diagram (they act on the scenario unit, not a view).
- Kill the implicit "last diagram" state = correct-by-construction (no fragile hidden target).
- Fix the inverse gap: when a diagram IS open with a selected element, the membership actions (esp. remove-from-this-diagram) MUST be present.
