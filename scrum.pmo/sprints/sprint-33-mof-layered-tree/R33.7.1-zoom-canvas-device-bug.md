## ARCHITECT DIAGNOSIS (robbin-architect 2026-07-31, MEASURED on served 0.8.30)
ROOT = TWO gaps, both leave the canvas un-grown on zoom-out:
1. **viewBox = TIGHT content bounds (no CANVAS_PAD).** `buildDiagramSvg` (diagram-view-model.ts:106): `vb = 0 0 max(maxX,100) max(maxY,100)` where maxX/maxY = per-box bounds + a per-box PAD only (:102-103). Design row B ("viewBox CANVAS_PAD = real placeable space") was NOT implemented → no extra placeable coordinate space even at scale 1.
2. **Zoom = pure CSS `scale` transform.** `RbPanZoom.apply()` (pan-zoom.ts:157-159): `content.style.transform = translate(tx,ty) scale(s)`. At scale<1 the content SHRINKS inside the SAME-size surface; the SVG element's rendered width/height AND the surface scroll-area are UNCHANGED. So zoom-out = smaller content in a fixed box, NOT a bigger canvas.
NET: R33.7.1 shipped only the scale-transform half (MIN 1→0.25); the canvas-GROW half never landed. `preserveAspectRatio="xMidYMid meet"` + no explicit SVG width/height means even a padded viewBox would just shrink apparent content (fit-to-container), not add visible room. Architect owns the under-spec: "viewBox canvas-pad" alone (row B) is INSUFFICIENT for the "canvas GROWS" intent — the fix must grow the CANVAS DIMENSIONS on zoom-out.
FIX DIRECTION (expert; reuse RbPanZoom, no fork): on zoom-OUT, GROW the SVG canvas's rendered dimensions / scrollable placeable area — e.g. give the SVG explicit width/height that scale as `canvasBase / scale` (at scale<1 → bigger px canvas) inside a SCROLLABLE surface, so boxes keep their coordinate size and the canvas around them grows = real room; pan/scroll the larger canvas within the fixed viewport. (Equivalently: zoom-out increases the placeable coordinate space + the rendered canvas px, not just the transform scale.) req: sharpen the R33.7.1 AC to a TESTABLE canvas-dimensions-grow measure (px growth on zoom-out), ride unit 754a1f9d. tester: assert SVG canvas width/height (or scroll area) INCREASES on zoom-out @390 + Tron device.

## ★ COMPOSITION PIN (architect, for expert's canvas-grow build 2026-07-31) — answers the 4 Qs
MODEL: `scale=1` is the boundary (1=100%=whole-diagram; canvasBase = the TIGHT content bounds = current viewBox maxX/maxY). TWO regimes, split at 1, continuous in canvas-px at 1:
- **scale ≥ 1 (MAGNIFY) — UNCHANGED:** RbPanZoom CSS-transform `translate(tx,ty) scale(s)` on `.dm-content`; SVG dims = canvasBase; viewBox tight; pan = CSS-translate. Preserves R32.11 drop-coord, R33.6.2 edge-autoscroll panBy, R33.6.3 reroute — DO NOT TOUCH the ≥1 path.
- **scale < 1 (CANVAS-GROW) — NEW:** SVG `width/height = canvasBase/scale` px; viewBox grows 1:1 (`0 0 maxX/scale maxY/scale`) so 1 unit→constant px ⇒ boxes keep VISUAL size + NEW empty coordinate space appears = room; CSS-transform = none (scale 1, translate 0); `.dm-surface` → `overflow:auto` = NATIVE scroll pans the grown canvas.

**(1) YES** — RbPanZoom.scale drives SVG DIMS (canvas-grow) for <1, CSS-transform MAGNIFY for ≥1. At scale=1 both = canvasBase (continuous). apply() branches on scale<1.
**(2) YES** — at <1, pan = native surface scroll (`overflow:auto`), DROP the CSS-translate; at ≥1 keep CSS-translate pan (unchanged). (Two pan mechanisms is intentional + LOWER risk than unifying — the ≥1 path stays byte-identical.)

At ≥1 both UNCHANGED.
**(4)** — canvasBase = current TIGHT viewBox maxX/maxY (content bounds). The DYNAMIC grow (`base/scale` on zoom-out) REPLACES the static CANVAS_PAD (design row B) — do NOT add a static pad; the zoom-out grow IS the room. At scale 1 = whole diagram (1=100%).
