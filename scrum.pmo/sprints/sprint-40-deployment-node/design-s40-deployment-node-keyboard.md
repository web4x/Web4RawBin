## R40.2 — MEASURED ARTEFACTS (real paths on WODA.prod / v60211; req mints the 3 refs to these)
- **DOMAIN (canonical source):** `Web4RawBin/.env` → `LE_DOMAIN=prod.wo-da.de` (:1) + `BASE_DOMAIN=prod.wo-da.de` (:2). Defined there (=values), consumed by code → `.env` IS the source (not a consumer). Ref = `ior:file:.env` key `LE_DOMAIN`/`BASE_DOMAIN`.
- **LE CERT (real):** `/etc/letsencrypt/live/prod.wo-da.de/` → `fullchain.pem` (5996B) · `privkey.pem` (3268B, 600) · `cert.pem` · `chain.pem` (Jul 31). Ref = the dir (or `fullchain.pem`).
- **SSH ⚠ (two catches — a phantom AND a semantic one):**
  - *Phantom:* there is **NO `Host WODA.prod` entry** in `~/.ssh/config` (it holds OUTBOUND hosts WODA.test/WODA.dev; WODA.prod=v60211 is the deploy TARGET) — a ref to that would be a FABRICATED path.
  - *Semantic (PO sharpening):* a UML **deployment node**'s "ssh config" = **how THIS NODE is configured as an SSH ENDPOINT (inbound service)**, NOT what it dials out. `~/.ssh/config` is the ossh-managed CLIENT (outbound) file — referencing it as "the ssh config OF WODA.prod" is **resolvable-but-SEMANTICALLY WRONG** (a truthful path answering the WRONG question — a subtler cousin of today's phantoms).
  - **CONFIRMED REFERENT SET (measured, resolves + answers the right question):** (1) **`/etc/ssh/sshd_config`** (3309B, HostKey/Port/PermitRootLogin — the node's SSH SERVICE config); (2) **`~/.ssh/public_keys/root.WODA.prod.public_key`** (the node's SSH IDENTITY). If the outbound client file is wanted at all, it is a **DISTINCT ref labelled `outbound-client-config`** (`~/.ssh/config`), NEVER conflated with the node's own. This makes the node genuinely describe the NODE: **service (sshd_config) + identity (pubkey) + domain (.env) + TLS (LE cert)** = what deployment-node style is FOR.

## R40.2 — UMLNode deployment-node model
- **NOT a new unit kind — an EXTENSION of the existing UML M2 set.** Measured: `diagram-view-model.ts` has an M2 facet catalog (`CLASS_FACETS = {class, interface, UmlClass, tsClass, ts-class-code}`) rendered by `renderFacet` (Method a6a05d34 / Impl 94ad4f50), arrowheads by M2 kind. `UmlNode` joins that catalog as a NODE facet-type (an `ior:class:ModelElement` like UmlClass/UmlInterface), NOT a bespoke unit type. One M1 unit for WODA.prod, instanceOf UmlNode M2.
- **STYLE renders via `renderFacet`, not a new renderer.** Add a `node`/`deployment-node` facet branch: the UML deployment-node shape (3D box / `<<node>>` stereotype) as a facet geometry in the existing facetW/facetH helpers + a shape branch in `renderFacet`. Reuse the facet-lens projection (R36.1/R36.2 (B)) exactly like the class-family default — one renderer, a new shape.
- **otmux items attach as CHILDREN by LENS, never mirrored (decided + justified).** The node holds a REFERENCE/lens to the LIVE otmux tree via the existing `OtmuxBridge.readSessionTree` (R31.3, Impl 5c1701bc) → the R31.4 3-type transient units (`otmuxSession → otmuxWindow → otmuxPane`). The tree RENDERS live items on read; the persisted graph stores ONLY the node + its lens, NOT a mirrored session/window/pane copy. **Justification:** a mirrored copy of live tmux state goes stale the instant a pane opens/closes and would churn the graph on every tmux change (violating INV-T + the consistency-by-construction doctrine — a generated view can't drift if it isn't stored). The lens reads live; the persisted identity is stable. This reuses R31.3/R31.4 wholesale.
- **INV-T byte-diff == 0:** R40.2 adds a NODE facet + an M1 node unit + a lens; it does NOT store live otmux state and does NOT touch the tree code (`mofChildren`) — persisted-graph churn = 0, tree byte-diff = 0. Chain: UC `deploymentNode.render` → Class DiagramViewModel → Method renderFacet (extend) → Impl; live-children ride the existing readSessionTree chain (no new persisted units for panes).

## R40.3 — Keyboard control
### (a) PREVENT the iOS soft-keyboard on the terminal input — DEVICE-VERIFY, do not assume
Real-WebKit @390 is the ONLY authority (Playwright-Chromium ≠ WebKit; I cannot measure this headlessly — [[visual-features-gate-by-pixel]] / [[real-webkit-390-headless-gating]]). DESIGN two candidates, gate on Tron's device:
- **Primary:** the terminal focus target is a `<div>` with **`inputmode="none"`** (+ `contenteditable` for caret/selection if needed) — modern WebKit honours `inputmode=none` to keep focus WITHOUT opening the soft keyboard. Keystrokes come from the R40.3 controller (below), not the soft keyboard.
- **Fallback:** a `readonly` (or `tabindex`-focusable non-input) element + a synthetic input path — the controller writes keystrokes straight to the ws PTY, the DOM element never receives native key events.
- **GATE:** on Tron's real iPhone @390 — tap the terminal → soft keyboard MUST NOT appear, terminal stays fully interactive via the controller. Screenshot-verify (not DOM-assert).

### (b) KEYBOARD CONTROLLER = data-driven key map (unit-backed, not hardcoded)
- An action-bar-like surface whose keys come from a **config UNIT** (a scenario unit / config holding rows of keys: `{ label, sequence (the bytes/escape to send), modifier?, width? }`). The controller RENDERS the config → each key on tap sends its `sequence` to the terminal via the same **R31.4 ws PTY** (PtyBridge.attachPane). So the FULL controller (arrows, Ctrl/Esc/Tab, macros) is a later CONFIG edit, **no rewrite** — the shell is generic, the keymap is data. Start with a minimal keymap unit (Esc/Tab/Ctrl/arrows/↵); expand by editing the unit.
- Reuses the terminal's existing ws PTY path; the controller is a client component reading the keymap unit.

### (c) LAYOUT — terminal fully visible at 390px (fix the occlusion)
- Current bug: the input row OVERLAYS the Scenario/Edit buttons and the keyboard occludes 100% of the terminal. FIX by construction with the CONCEPT viewport primitives (design-CONCEPT-scrollable-viewport-architecture.md): terminal + keyboard-bar are **compartments in a vertical strip** — the keyboard-controller is a fixed **bottom bar** (its own compartment), the terminal fills the remaining height in a scrollable viewport ABOVE it, and the input row is repositioned OUT of the Scenario/Edit buttons' space. No full-screen overlay → the terminal is never occluded. @390: bottom bar (keys) + terminal viewport above, both visible; GATE by screenshot @390.
- INV: presentation != function (the CONCEPT doctrine) — the keyboard-bar is a position, not a mode that hides the terminal.
